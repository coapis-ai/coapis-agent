## 0. 结论摘要

三大症状全部实锤，根因不是零散 bug，而是**架构性脑裂**：

| 症状 | 根因 | 证据 |
|---|---|---|
| 每个任务每次触发执行 3 次 | `start()` 非幂等 → 3 个孤儿 CronManager 共读一份 jobs.json | 日志 15:55:04 三连注册；今日 04:10:04 喝水提醒同秒 3 次 |
| agent 型任务必败 | 字符串 input 撞 `AgentRequest.input: List[Message]` 校验 | 今日 04:11:04 受控实验复现 |
| dream 每日必炸 | legacy 装配的 `MemoryManager` 无 `dream()` 方法 | 日志 23:00:00 ×4 |
| （隐患）跨用户越权执行 | legacy 路径构造 CronManager 不带 `owner_user_id`，所有权校验被跳过 | 代码 workspace.py:1415-1421 |

## 2. 根因分解

### RC-1 重复执行：start() 非幂等 + 注册无生命周期
- `coapis/agents/workspace.py:552` `start()` **无任何幂等保护**（无早退、无锁），`status="running"` 直到第 1399 行（约 1.4s 后）才置位；
- `multi_agent_manager.py:429` `start_all()` 以 `status != "running"` 判定 → 启动窗口内的并发调用全部再次进入 `start()`；
- 实测 3 路并发（服务启动 + 首个请求 + 管理探测）→ 3 次 start → 3 个 CronManager；
- 放大因素：
  - `registry.get_or_create` 懒创建"裸管理器"（潜在第 4 个实例）；
  - `global_default` 工作区自带 CronManager（`owner_user_id=None`，不入 registry）；
  - **registry 无 deregister/unregister**，workspace.stop() 不清理注册表。

### RC-2 agent 任务必败：input 契约断裂
- `CronJobRequest.input: Optional[Any]`，用户/前端天然传字符串；
- executor 原样透传 → 框架 `AgentRequest.input` 要求 `List[Message]` → 必败；
- 失败被 `_execute_once` 捕获记 `last_status=error`（日志可见），但**用户侧无任何通知**。

### RC-3 dream 装配断裂
- legacy 装配（workspace.py:363）与 `_dream_callback` 的期望不一致；
- `runner.py:163` 声明 `memory_manager: BaseMemoryManager | None = None`，实际由 legacy workspace 注入简易版。

### RC-4 多用户隔离缺陷（结构性）
1. **所有权校验失效**：legacy 构造 CronManager（1415-1421）**不传 `owner_user_id`** → executor 的 owner 校验被跳过 → 恶意/误造的 job 指定任意 `target_user_id` 也能执行并把结果投给对方通道（利用门槛高，架构风险大）。
2. **任务不绑 agent**：`CronJobSpec` 有 `agent_id` 字段（实测默认 `"default"`），但 executor 第 225 行**强制** `set_current_agent_id(f"user:{target}")` → 任何子 agent 创建的任务都在默认 agent 上下文执行（提示词/工具/记忆隔离形同虚设）。
3. **双 jobs.json 脑裂**：用户级 `workspaces/X/crons/jobs.json` 与子 agent 级 `workspaces/X/agents/A/crons/jobs.json` 是两个文件 → 切换活跃 agent 时任务"消失"。
4. **registry 语义缺陷**：username 键 + 最后写入胜出 + 无注销 → API 可能操作到孤儿/裸管理器；workspace 重载后旧实例悬空。
5. **global 工作区 cron 失控**：无 owner、不入 registry、任何用户 API 不可见。
6. **共享文件并发写**：多管理器读写同一 jobs.json → 内存列表分叉 → 后写覆盖先写（一方新建任务被另一方旧列表冲掉）。
7. **同刻碰撞**：3 次执行共用同一隔离会话 ID `cron:{job}:{ts}`（秒级时间戳）→ 并发写同一会话，消息交错损坏。

### RC-5 健壮性缺口
1. 失败/超时无用户侧通知（仅日志）；超时算 cancelled 不算 failed；
2. 执行历史仅内存 deque（`_record_execution`），重启即失，无持久台账；
3. 投递失败仅 warn，无重试/死信；
4. 无熔断：坏任务每分钟轰炸日志（生产 coapis.log 曾达 8.5GB）；
5. 隔离会话无限累积，无保留策略；
6. `update_job` 删旧建新存在"任务不存在"窗口；
7. `misfire_grace_time=60`：事件循环卡顿 >60s 时 tick 静默丢弃；
8. 时区取全局配置，不支持 per-user。

## 3. 方案设计

**原则：每用户单一调度器（single source of truth）；显式归属；任务绑定 agent；失败可见。**

### 第一批：止血（小改动，消除重复执行 + 必败）
- **F1 幂等 start()**：legacy `workspace.start()` 增加早退（`status=="running"` 直接返回）+ `asyncio.Lock` 串行化 + 状态机 `stopped→starting→running`（starting 期间并发调用等待而非重建）。
- **F2 registry 生命周期**：`register_manager` 识别旧实例（非自身）先 `stop()` 再替换；新增 `unregister(username)`，`workspace.stop()` 调用；裸管理器打标，workspace 真实管理器到达即接管。
- **F3 input 归一化**：executor 入口统一把 `str` / `list[str]` / 混合内容包装为合法 Message 列表，覆盖全部任务类型。
- **F4 dream 修复**：`MemoryManager` 补最小 `dream()`（合并去重记忆文件）；`_dream_callback` 加 hasattr 防御。
- **F5 孤儿清零验证**：部署后断言每用户恰 1 个 CronManager（启动日志计数 + 单测）。

### 第二批：多用户隔离加固
- **F6 每用户单一 jobs.json**：所有工作区（含子 agent、global）统一指向 `workspaces/{username}/crons/jobs.json`；存量子 agent 级文件做一次迁移合并。
- **F7 强制 owner**：一切 CronManager 构造必须带 `owner_user_id`；executor 严格校验（含 global 工作区）；API 禁止普通用户创建 `target_user_id≠self` 的任务（admin 除外）。
- **F8 任务绑 agent**：executor 改用 `job.agent_id`（缺省回退默认 agent）；API create 接受 agent_id；执行上下文按任务所属 agent 建立。
- **F9 会话 ID 唯一化**：隔离会话 `cron:{job}:{uuid4}`，消除同秒碰撞。

### 第三批：健壮性与可观测
- **F10 持久执行台账**：新表 `cron_executions`（job_id, user_id, agent_id, started_at, finished_at, status, duration_ms, error, session_id），PG+SQLite 双方言，对齐现有迁移体系；API `GET /api/cron/jobs/{id}/executions`。
- **F11 失败闭环**：失败/超时向用户通道发失败通知；连续 3 次失败自动暂停任务 + 通知（熔断）。
- **F12 会话保留**：每任务保留最近 50 次隔离会话，超出自动清理。
- **F13 原子更新**：update 改为 swap（先加新后删旧）。
- **F14（可选）per-user 时区**。

### 工作量估算
第一批 ~0.5 天 ｜ 第二批 ~1 天 ｜ 第三批 ~1 天
