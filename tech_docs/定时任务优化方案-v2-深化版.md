## 1. 对 v1 结论的代码核验与修正

### 修正 ①：F1 前提过时 —— 三重执行的真根因在上游（最重要）

v1 称"CronManager.start() 无幂等保护"。**核验：`manager.py:148-151` 已有 `async with self._lock: if self._started: return` 守卫。** 给 start() 再加守卫无效。

真根因是一条四环节链（均已定位到行号）：

| # | 缺陷 | 位置 |
|---|------|------|
| R1 | `Workspace.start()` 无任何幂等保护，同一实例并发两次 start → 各自 new 一个 CronManager，前者泄漏且持续调度 | `agents/workspace.py:552` |
| R2 | `get_agent` 快速路径在**锁外**对未启动的 workspace 直接 `await ws.start()`，且不声明 `_pending_starts`，可与创建者竞态 | `app/multi_agent_manager.py:152-157` |
| R3 | `create_agent` 插缓存时不声明 pending；创建者在 `:178` 覆写缓存键，被覆写的已启动实例永不 stop | `app/multi_agent_manager.py` create_agent / `:178` |
| R4 | `register_manager` 替换 registry 条目时**不停旧 manager**（懒加载 manager 泄漏） | `app/crons/registry.py:69-78` |

任一环节命中即产生"同用户多 manager 同调一份 jobs.json"，与日志中 ×3 完全吻合。
另注：`app/workspace/workspace.py`（新 workspace 类，带 cron_manager service 定义）当前**未被 MamAgentManager 引用**，属平行死代码，清理时一并处理。

### 修正 ②：F7 已半落地

API 层已在 create/replace 强制 `target.user_id = current_user`（`crons/api.py:103-105 / 133-135`）。UI 路径跨用户定向已不可能。
残余缺口只在 **executor 层断言** + **agent 工具路径**（见 N2）。

### 修正 ③：迁移编号确认

alembic 最新为 `0007_tasks_menu`，执行历史新表应为 **0008**。

### 其余 v1 项核验结果（维持不变）

- 输入字符串 vs `List[Message]` 校验必败 → 属实（F3 保留）。
- 执行历史仅内存 deque、重启即失 → 属实（F10 保留）。
- dream 目标对象错误 → 属实，且已确认正确接法：`ReMeLightMemoryManager.dream()` 存在（`agents/memory/reme_light_memory_manager.py:638`），经 `workspace.runner.memory_manager` 可达（F4 保留）。
- 心跳会话无清理 → 属实（F9 保留）。
- v1 怀疑过的 `_cleanup_heartbeat_sessions` 中 `data_root` 未定义 → **不实**：`manager.py:545` 有 `data_root = WORKING_DIR`，撤销该疑虑。

## 2. v1 未发现的新缺陷

### N1（根因级）：三重执行四环节链
即上文修正①。这是"任务没生效/重复执行"体验问题的头号元凶。

### N2（高危，跨用户污染）：agent 工具随机抓 manager
`agents/tools/cron_scheduler.py:35-52`：
```python
if registry._managers:
    for username, mgr in registry._managers.items():
        return mgr          # ← 取字典里第一个，与当前用户无关
```
任何 agent 调 `cron_scheduler` 工具建的 job 都会落到**迭代顺序碰到的某个用户**的调度器：
- job 写进别人的 jobs.json（数据越权）；
- owner 判定、投递、隔离全部错位；
- 多用户环境下行为不可预测。

修复依赖：`app/agent_context.py` 现有 `agent_id / session_id / root_session_id` 三个 ContextVar，**没有 username**。需新增 `current_username` ContextVar，在鉴权中间件 / runner 入口处 set，工具侧据此 `registry.get_user_cron_manager(username)`。

### N3（系统性）：时区默认 UTC
- `ScheduleSpec.timezone` 默认 `"UTC"`（`crons/models.py`）；
- 前端 `constants.ts:8 DEFAULT_TIMEZONE="UTC"`，拉取用户时区失败时**静默回退 UTC**（`CronJobs/index.tsx:34-41` 仅 console.error）；
- 效果：国内用户设"每天 08:00"实际 16:00 触发。任务"在跑"但时间全错 → 强烈贡献"没生效"观感。

修复：创建时默认填用户时区（后端 config `user_timezone` 已有全局值）；前端时区为空时禁止提交并在表单显式标注；列表已展示 tz 列（`columns.tsx:159`）保持。

### N4（健壮性）：agent 型任务 120s 默认超时
`JobRuntimeSpec.timeout_seconds` 默认 120（`models.py:104`），`executor.py:263-267` 用 `asyncio.wait_for` 硬杀。agent 型任务超过 2 分钟即被取消 → "执行了没结果"。
修复：agent 型默认提到 600s；UI 暴露该字段（当前不可配）。

### N5（死代码，隐患）：legacy `routers/cron.py`
独立一套 `cron_jobs.json` 存储 + 内存缓存，`POST /run` 是**假成功桩**（直接返回 `{"success": True}` 不执行）。全仓无引用、未挂载。风险：后人误挂载即产生第二套假系统。处置：移入 `.trash`。

### N6（次要）：心跳细节
- 心跳请求 `user_id = agent_id`（`heartbeat.py:172`）→ 会话落到 `workspaces/user:alice/chat/`（冒号目录名）；
- 心跳超时硬编码 120s（`heartbeat.py:181`）；
- 建议随心跳一并规整（低优先级，可并入 B 批顺手改）。

### N7（投递盲区细化）：失败零通知
执行失败的 job 只进内存 deque，用户端无任何信号。实现路径已通：`manager.py:726-735` 成功路径已有 `channel_manager.send_text(target_user_id, ...)` 先例，失败路径复用同款即可。

### N8（测试空白）：cron 子系统单元测试为零
仅存 `docker/test_cron.py` 老探针脚本。v1 的"回归矩阵"实为从零建设，工作量应计入 B 批。

## 3. 修订后的执行计划

### A 批 · 止血（消除三重执行 + 跨用户污染）★最高优先级
| 项 | 内容 | 对应 |
|----|------|------|
| A1 | `Workspace.start()` 幂等守卫（Lock + `_started`） | R1 |
| A2 | `get_agent` 快速路径并入 `_pending_starts` 认领协议（未启动的缓存实例视同 pending） | R2 |
| A3 | `register_manager` 替换前优雅 stop 旧 manager | R4 |
| A4 | 废弃 `workspace.start()` 内 legacy 内联 cron manager，统一经 registry 获取（顺带补 `owner_user_id`，消掉 RC-4.1） | R3+RC-4.1 |
| A5 | `cron_scheduler` 工具按 `current_username` ContextVar 解析 manager（新增 ContextVar + 中间件注入） | N2 |
| A6 | legacy `routers/cron.py` 移入 .trash（平行死代码 `app/workspace/workspace.py` 暂留标记 TODO） | N5 |

## 4. 风险与回滚

- **A 批触碰 workspace 启动热路径**（登录必经之路）：dev 先行，观察 ≥24h 再上生产；改动集中在 4 个文件（workspace.py / multi_agent_manager.py / registry.py / cron_scheduler.py + 中间件），无数据迁移，回滚 = revert。
- B/C 批均为纯增量（C3 新表除外，可独立 drop）。
- 每批独立 commit、独立可回滚；A→B→C 顺序不可颠倒（C 的 owner 断言依赖 A4 的 owner 填充）。
