# 消息系统整体设计方案 v1

> 范围：CoApis 社区版 + 企业版
> 前提：社区版定义接口与默认实现，企业版只注入存储与扩展，不重复造接口
> 日期：2026-10-01

---

## 一、现状盘点（全部经代码实证）

### 1.1 已有的东西

| 部件 | 位置 | 状态 |
|---|---|---|
| 渠道发送架构 | `server/coapis/app/channels/` | 成熟。16+ 渠道适配器（console/钉钉/飞书/企微/Discord/Telegram 等）+ 统一队列管理器 + `send_text()` |
| 主动推送接口 | `server/coapis/app/routers/messages.py` | 可用。`POST /api/messages/send`，智能体可向任意渠道推文本。**发了就忘：不落库、无回执、无追踪** |
| 消息中心页面 | `client/src/pages/Messages/`（约 800 行） | 半成品。统计面板、分类统计、列表表格、详情信息、回调状态、处理时间线、操作面板七个组件齐全 |
| 前端类型契约 | `client/src/api/types/message.ts`、`message_detail.ts` | 完整。定义了 5 种业务类型、7 种工作流状态、优先级、已读标记、回调信息、审批信息、时间线事件 |
| 前端 API 模块 | `client/src/api/modules/message.ts`、`message_detail.ts` | 指向 `/api/ent/messages/*` —— **这套后端接口完全不存在** |
| 路由 | `MainLayout/index.tsx` | `/messages` 已注册（注释标着 placeholder），菜单里没有入口 |

### 1.2 缺失的东西（这就是"半成品"的断点）

1. **后端零实现**：前端调的 5 个接口（stats / categories / list / detail / mark-as-read）一个都没有，页面必然空白报错。
2. **没有生产者**：审批、任务完成、外部回调、系统事件——没有任何一处会"产生一条消息"。审批服务（`approvals/service.py`）甚至是纯内存的，一小时后被垃圾回收，痕迹全无。
3. **没有存储**：消息既不进 JSON 也不进数据库，来了就丢。
4. **没有实时触达**：websocket 只有 `/ws/chat/{agent_id}` 一条聊天流，Web 前端收不到"有新消息"的推送，顶栏也没有铃铛角标。
5. **收发两条腿断开**：渠道推送是发后即忘，消息中心看不到；消息中心里的消息也无法反向触发渠道推送。

### 1.3 一句话诊断

**契约（前端类型）画得很好，管道（后端）一根没铺，水源（生产者钩子）一口没开。** 这不是修补问题，是要按契约把整条管道建起来。

## 二、总体架构

```
 生产者(Producer)                     消息总线(MessageBus)              消费者(Consumer)
┌─────────────────────┐         ┌──────────────────────────┐        ┌─────────────────────┐
│ 审批 发起/通过/拒绝  │────────▶│                          │        │ REST: /api/messages │
│ 任务 完成/失败       │         │  notify() 统一入口        │───────▶│   (列表/详情/已读/  │
│ 外部系统 回调到达    │         │  ① 落库(repository)       │        │    统计/筛选)       │
│ 智能体 主动推送      │         │  ② 追加时间线事件         │        │ WS: /ws/notify     │
│ 系统事件(备份/告警)  │         │  ③ 实时广播              │───────▶│   (新消息/状态变更) │
└─────────────────────┘         │  ④ 可选:联动渠道推送      │───────▶│ 顶栏铃铛角标+红点   │
                                └──────────┬───────────────┘        └─────────────────────┘
                                           ▼
                              ┌──────────────────────────┐
                              │ MessageRepository(抽象)   │
                              │ 社区版: SQLite 单文件      │
                              │ 企业版: PostgreSQL 注入   │
                              └──────────────────────────┘
```

三条铁律：

1. **一切消息必经 MessageBus**——不管谁产生，都走同一个 `notify()` 入口，保证格式统一、时间线完整、可追溯。
2. **存储只认 Repository 接口**——社区版默认 SQLite，企业版通过既有插件机制注入 PG 实现（与标签服务的 JSON→DB 双路模式同款）。
3. **接口一套、前缀统一**——全部收敛到 `/api/messages/*`，企业版**不**新建 `/ent/messages`（符合企业版开发原则：不新增与社区版同名的重复接口）。

## 三、数据模型（对齐现有前端契约，兼容不推翻）

### 3.1 消息主体 `messages`

沿用前端 `MessageListItem` 已定义的字段（前端不用大改）：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | UUID | 主键 |
| user_id | string | **收件人**（新增，契约里没有，必须加；社区版单用户也写死为当前用户） |
| scene_id | string? | 关联场景（可为空） |
| business_type | enum | approval_request / callback_notification / external_system_status / ai_agent_task / system_notification（沿用契约） |
| workflow_status | enum | pending_approval / processing / callback_pending / callback_success / completed / rejected / failed（沿用契约） |
| source_type | string | 来源标识：agent_id / external_system 名 / system |
| source_ref | string? | 跳转锚点（新增）：会话 id、审批 request_id、外部系统 id，点击消息可直达现场 |
| title / summary / content | string | 标题/摘要/正文 |
| priority | enum | high / medium / low |
| is_read / read_at | bool / time | 已读标记与时间 |
| channel | string? | 若联动了渠道推送，记录渠道名 |
| created_at / updated_at | time | 时间戳 |

### 3.2 时间线 `message_events`（append-only）

| 字段 | 类型 | 说明 |
|---|---|---|
| id / message_id | | 外键 |
| event_time | time | |
| event_type | enum | received / ai_classified / mark_read / approval_submitted / approval_approved / approval_rejected / callback_sent / callback_success / callback_failed（沿用契约） |
| description | string | |
| operator | string? | 操作者 |

时间线是审计友好的追加流，任何状态变更都追加一条，**不修改**原消息行（workflow_status 例外，允许更新）。

### 3.3 存储介质选择（决策点 D2）

- **推荐：SQLite 单文件**（`{data_dir}/messages.db`）。理由：消息天然是"分页 + 多条件筛选 + 计数统计"查询，JSON 文件做不到高效过滤；社区版已有 SQLite 使用先例（cleanup 模块）。
- 备选：JSON（与 tags 一致）。不推荐，性能差且并发写易坏。
- 企业版：PG 两张表 `messages` + `message_events`，字段同上。

## 四、模块设计

### M1 存储层（社区版 1.0 人日）

- 新增 `services/message_repository.py`：抽象基类，方法固定为 `create / get / list(筛选+分页) / update_status / mark_read / add_event / get_events / stats / category_stats / delete(归档)`。
- 社区版实现 `SqliteMessageRepository`；企业版在 `coapis-pro/server/coapis/enterprise/database/` 注入 PG 实现，走既有 `register_plugin()` 通道，与用户仓储同一套路。
- 归档策略：已读且超过 90 天的消息，夜间任务移到 `messages_archive`（社区版同库异表，企业版同表分区或异表均可）。

### M2 生产层（社区版 1.5 人日）

新增 `services/message_bus.py`，对外只有一个门面：

```
await notify(business_type, title, summary, content, *,
             user_id, priority, source_type, source_ref=None,
             workflow_status="processing", push_channels=None)
```

内部做四件事：落库 → 追加 received 事件 → WS 广播 → （可选）联动渠道推送。

**首批内置钩子（决策点 D4）**：

| 钩子 | 时机 | business_type | 说明 |
|---|---|---|---|
| 审批 | 发起 / 通过 / 拒绝 | approval_request | 改造 `approvals/service.py`，三个节点各发一条；顺带把审批记录从纯内存改成落库（至少落一条消息，审批本体二期再迁） |
| 任务 | 后台任务/定时任务 完成 / 失败 | ai_agent_task | 挂在任务收尾处 |
| 智能体 | `/api/messages/send` 调用成功 | system_notification | 现有接口升级为"经 Bus 发送"，推送成功后自动生成消息记录，收发从此闭环 |
| 系统 | 备份完成/失败、磁盘告警 | system_notification | 挂在 cleanup/backup 收尾处 |
| 外部系统 | 回调到达/成功/失败 | callback_notification / external_system_status | **二期**，依赖外部系统回调链路稳定后再接 |

### M3 服务层 + REST API（社区版 1.0 人日）

新增 `routers/messages_center.py`（与现有 `messages.py` 并存，后者只管渠道发送）：

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/messages/list` | POST | 分页 + 筛选（business_type / workflow_status / is_read），对齐前端 `getList` |
| `/api/messages/{id}` | GET | 详情 + 时间线 + 回调/审批扩展信息 |
| `/api/messages/mark-as-read` | POST | 单条/批量已读 |
| `/api/messages/stats` | GET | 总数/未读/今日新增/处理中 |
| `/api/messages/categories/stats` | GET | 按 business_type 分组计数 |

前端 `api/modules/message.ts` 里五个 URL 的 `/api/ent/` 前缀**改掉**（决策点 D1，见第七节）。

### M4 实时投递（社区版 1.0 人日）

- 新增独立轻量连接 `GET /ws/notify`（鉴权同 chat ws）。不复用 chat ws 的原因：chat ws 按 agent 维度建立且生命周期绑聊天，消息推送应跨会话、跨 agent、全局一份。
- 下行事件两种：`{"type":"message.new","id":...}` 和 `{"type":"message.updated","id":...}`（状态变更时）。
- 前端建一个全局 `useMessageCenterStore`：订阅 notify ws，维护未读数；断线重连后拉一次 stats 校准。
- **决策点 D3**：若不想加第二条连接，可降级为 30 秒轮询 stats 接口（省 0.3 人日，体验差一档）。推荐真 WS。

### M5 前端完善（2.0 人日）

1. **详情页**：补 `/messages/:id` 路由，用现成的 `MessageDetailInfo` + `ProcessingTimeline` + `CallbackStatusPanel` + `MessageActionPanel` 四个组件拼装（组件都在，只差组装和接线）。
2. **顶栏铃铛**：`HeaderButtons/` 新增 `NotificationBell.tsx`，图标 + 红色数字角标，点击展开最近 10 条下拉，"查看全部"进消息中心。位置与前端深化方案 v2.2.2 的顶栏按钮区合并设计（快切、模型选择、设置旁边）。
3. **菜单项**：动态菜单里加"消息"一项（走既有标签/菜单管理接口配置，不硬编码）。
4. **列表行点击**：现在只 `console.log`，改为跳详情；有 `source_ref` 的加"前往现场"按钮（跳会话/审批/外部系统页）。
5. **实时刷新**：订阅 notify ws，新消息到达时列表插入 + 角标 +1 + 轻提示音（可关）。

### M6 渠道联动（0.5 人日）

- `/api/messages/send` 改造：发送结果（成功/失败）写回对应消息的时间线（callback_sent / callback_success / callback_failed），消息行记录 channel 字段。
- `notify(push_channels=[...])` 支持一条站内信同时推到指定渠道（如审批同时推钉钉），失败重试 3 次后进时间线。

### M7 企业版扩展（1.5 人日）

- PG 两表 + PG 仓储实现，`register_plugin()` 注入（复用 users 仓储已趟通的路径）。
- 可见性：普通用户只看 `user_id=自己`；管理员额外 `/api/messages/admin/list` 看全员（复用既有 admin 权限中间件）。
- 审计联动：消息创建/已读事件同步写 `audit_log`。
- 保留期可配（环境变量 `MESSAGE_RETENTION_DAYS`，默认 90）。

## 五、社区版 / 企业版职责划分

| 层 | 社区版 | 企业版 |
|---|---|---|
| 数据模型 | 定义（messages + message_events） | 同构建表 |
| 存储 | SQLite 默认实现 | PG 实现注入 |
| 生产钩子 | 全部（审批/任务/智能体/系统） | 不新增 |
| REST API | 全部 5 个接口 | 仅 admin 全局视图 1 个 |
| 实时推送 | /ws/notify | 复用 |
| 前端 | 全部（页面/详情/铃铛/实时） | 不新增页面 |
| 审计/保留期 | 基础保留 | 审计联动 + 可配保留期 |

企业版自查清单对照：无同名 router ✅、无重复页面 ✅、无新环境变量（除保留期一个，属配置非开关）✅、不改社区版代码 ✅。

## 七、决策点（需拍板）

- **D1 接口前缀**：前端 `/api/ent/messages/*` 改为 `/api/messages/*`（社区版实现、企业版换存储）。强烈建议，否则违反企业版"不建重复接口"原则。**默认按此执行**。
- **D2 社区版存储**：SQLite（推荐）vs JSON。**默认 SQLite**。
- **D3 实时方式**：独立 `/ws/notify`（推荐）vs 30 秒轮询。**默认 WS**。
- **D4 首期钩子范围**：审批 + 任务 + 智能体推送 + 系统事件，外部回调二期。**默认按此**。
- **D5 可见性**：首期仅本人可见，admin 全局视图放企业版第三波。**默认按此**。

以上五项若无异议，按默认值执行。

## 八、验收标准（总）

1. 发起一次审批 → 消息中心出现 1 条 pending_approval 消息，通过后变 approved，时间线 ≥3 条事件。
2. 后台任务失败 → 出现 high 优先级 ai_agent_task 消息。
3. 智能体调 `/api/messages/send` → 渠道收到文本，同时消息中心有记录且时间线含 callback_success。
4. 新消息产生时，已登录 Web 的用户 1 秒内看到角标 +1（不断网前提下）。
5. 标记已读后 stats.unread_count 减 1，刷新页面状态不丢。
6. 企业版环境下数据落 PG，社区版代码零改动。
7. 90 天前已读消息进入归档，列表不可见但归档表可查。

## 九、风险

| 风险 | 应对 |
|---|---|
| 审批服务改造牵连 tool_guard 链路 | 只在审批服务里"旁路发消息"，不改审批判定逻辑；第一波单独回归审批用例 |
| notify ws 与 chat ws 并存带来连接数翻倍 | notify 是无状态广播，开销极低；移动端可降级轮询 |
| 消息量增长后 SQLite 锁竞争 | 单文件 WAL 模式 + 夜间归档；企业版天然走 PG |
| 半成品 UI 字段与新模型有出入（如 user_id 契约缺失） | 契约向后兼容：新增字段均为可选，前端小改即可 |
