# 文档解析基础能力故障定位（DOCX/PPTX/XLSX/PDF）

日期：2026-10-15 ｜ 环境：dev（coapis-server-dev）复现 + 生产镜像实测
状态：**仅分析，代码 0 行未改**

---

## 0. 一句话结论

Word 读不出来不是"模型不会读"，是四件事叠加：

1. **前端"引用文件"传的是非法 `file://` URI** → 后端解析不出路径 → 模型收到 `[Error: Unknown file source type or empty data]`；
2. **runner 注入的提示词给的是虚拟路径**（`/AI_Agent技术总结报告.docx`，磁盘上不存在）；
3. **doc_reader 的相对路径按进程 CWD（`/app`）解析**，与 read_file（按 `workspace/files/` 解析）语义不一致 → 智能体在"read_file 能读到二进制、doc_reader 说文件不存在"之间反复试错；
4. **所有兜底路径在镜像里都不存在**：无 markitdown/pandoc/pdftotext/libreoffice；护栏硬拒 `python3 -c`；技能文档偏偏引导智能体去用这些被拒的命令。

**上传附件路径是通的，文件引用（聊天框"+"选文件）路径是断的。** 生产镜像还额外缺 `python-pptx / openpyxl / pymupdf4llm`，所以生产环境 PPT/Excel/PDF 必失败。

## 1. 复现证据链（全部实测，非推测）

### 1.1 前端发出的 file 块形态（根因 1）

`client/src/pages/Chat/index.tsx:1455-1472`

```ts
const filePath = file.path.startsWith('/') ? file.path.slice(1) : file.path;
rewrittenContent.push({
  type: "file",
  source: { url: `file://${filePath}` },   // ← file://AI_Agent技术总结报告.docx
  filename: file.name,
});
```

`file://名字` 是**非法 file URI**：`file://` 后第一段是 authority（主机位），不是路径。合法形态是 `file:///绝对路径`。

后端实测（dev 容器，workspace=admin）：

| 前端形态 | `_extract_source_and_filename` 结果 | `_process_single_file_block` 结果 |
|---|---|---|
| `source.url = "file://AI_Agent技术总结报告.docx"`（**当前线上形态**） | `{'url': 'file://AI_Agent...'}` | **`None`** → 块被替换为 `[Error: Unknown file source type or empty data]` |
| `source.url = "/AI_Agent技术总结报告.docx"` | `file:///apps/ai/coapis/workspaces/admin/files/AI_Agent...docx` | ✅ `/apps/ai/coapis/workspaces/admin/files/AI_Agent技术总结报告.docx` |
| `file_url = "/media/AI_Agent技术总结报告.docx"`（上传附件形态） | 同上 | ✅ 同上 |

代码路径：`_resolve_media_url()` 对 `file://` 前缀**短路返回原串**（message_processing.py:179），不做任何解析；`_process_single_file_block()` 用 `urlparse().path` 取路径，`file://名字` 的 `path` 为空串 → `url2pathname("")=""` → 返回空 → `_handle_download_failure()` 给出那句错误占位符。

### 1.2 提示词给的是虚拟路径（根因 2）

`server/coapis/app/runner/runner.py:1648-1662`

```
[用户选择了以下文件：AI_Agent技术总结报告.docx (path: /AI_Agent技术总结报告.docx)。
 请使用 doc_reader 工具读取这些 DOCX 文件。文件路径已提供，无需搜索。]
```

`path` 是前端级联菜单的**虚拟全路径**，磁盘上不存在。目录引用分支（`dir_refs`）此前已修成"给真实绝对路径 + 真实工具名"（A1 改造），**文件引用分支（`file_refs`）漏了**，还在给虚拟路径。

### 1.3 doc_reader 相对路径解析错位（根因 3）

`server/coapis/agents/tools/doc_reader.py` 用 `Path(file_path).resolve()` → 相对路径在**进程 CWD** 解析；容器 CWD = `/app`。
`server/coapis/agents/tools/file_io.py:_resolve_read_path()` 相对路径在 `workspace/files/` 解析。

实测（dev 容器）：

```
PATH: files/AI_Agent技术总结报告.docx        -> {'error': '文件不存在: files/...'}
PATH: /AI_Agent技术总结报告.docx             -> {'error': '文件不存在: /...'}
PATH: /apps/ai/coapis/workspaces/admin/files/AI_Agent技术总结报告.docx
     -> {'action':'read','chars':278,'format':'python-docx','content':'AI Agent 技术总结报告…'}
```

→ **docx 解析本身是好的，python-docx 在 dev 镜像里已装；只要路径给对就能读。**

### 1.4 模型看不到 file 块，只看得到提示词里的路径

agentscope `OpenAIChatFormatter.supported_blocks = [Text, Image, Audio, ToolUse, ToolResult]`，
`file` 块落到 `else: logger.warning(...)` 被**静默丢弃**。
→ 路径信息**只能**靠 runner 注入的提示词传递。1.1 + 1.2 同时断掉，模型就彻底没有路径可用，只能靠 `read_file` 猜 → 读到 ZIP 二进制（用户看到的"二进制 ZIP 格式内容"）。

### 1.5 兜底路径全灭（根因 4）

镜像内 CLI 二进制实测（dev / mycom-server / mycom-ent 三镜像一致）：

```
MISS markitdown   MISS pandoc   MISS pdftotext   MISS libreoffice
MISS soffice      MISS antiword MISS catdoc
```

→ `doc_reader` 里 `_read_pdf/_read_docx` 的 markitdown、pdftotext 兜底是**纯装饰**，永远走不到。

护栏实测（`WorkspaceGuard.is_command_allowed`）：

| 命令 | user | admin | 说明 |
|---|---|---|---|
| `python3 -c "import zipfile"` | DENY | DENY | `FALLBACK_DANGEROUS_PATTERNS` P0 硬拒（workspace_guard.py:162）——**设计如此** |
| `pandoc -f docx -t markdown x.docx` | DENY | DENY | 不在白名单（且二进制也不存在） |
| `markitdown x.docx` | DENY | DENY | 同上 |
| `file -b --mime-type x.docx` | DENY | DENY | file_reader 技能第一句就让智能体跑这个 → 必被拒 |
| `unzip -p "x.docx" word/document.xml` | ALLOW | ALLOW | 唯一可用的 shell 兜底，智能体不知道 |

审计日志实证（dev，2026-10-15 04:25-04:26，session d1a79492）：

```
tool_guard_denied  tool=execute_shell_command  reason="auto_denied by tool guard"
  command: python3 -c "...zipfile...word/document.xml..."
workspace_guard  allowed  /apps/ai/coapis/skill_pool/docx/SKILL.md
tool_guard_denied  （第二次，同样的 python3 -c）
```

→ 智能体的行为完全合理：doc_reader 报"文件不存在" → read_file 读到二进制 → 想到用 python 解 zip → 被护栏拒两次 → 去读 docx 技能 → 技能让它跑 shell/CLI → 全堵 → 道歉。**这是系统把路堵死了，不是模型能力问题。**

### 1.6 生产镜像依赖缺口（根因 5）

```
coapis-server-dev        : docx OK  pptx OK  openpyxl OK  pymupdf4llm OK
coapis-mycom-server 1.0.9: docx OK  pptx ✗  openpyxl ✗  pymupdf4llm ✗
coapis-mycom-ent-server  : docx OK  pptx OK  openpyxl OK  pymupdf4llm ✗
```

`server/requirements.txt:127-133`：

```
# python-pptx 在 dev 与生产运行环境里都缺失（openpyxl/python-docx 已由镜像或
# shared_runtime 提供，无需重复声明）。
python-pptx>=1.0.0
# pymupdf4llm>=0.1.0
# python-docx>=1.1.0
# openpyxl>=3.1.0
```

注释断言"openpyxl 已由镜像提供"——**对社区版生产镜像不成立**（实测 FAIL）。`pyproject.toml` 的 `[documents]` extras 四个全声明，requirements.txt 只落地 1 个 → 两份清单不一致（此前依赖体检的同类问题）。

### 1.7 技能层与护栏自相矛盾

`skill_pool/` 下 docx / pdf / pptx / xlsx / file_reader 五个技能（Anthropic 风格）全部要求：

```
> 运行方式: cd {this_skill_dir} && python scripts/...
> 或使用 execute_shell_command 的 cwd 参数
```

- 技能脚本目录在 `skill_pool/`（工作区外）→ admin 角色 `python3 *.py` 因"文件必须在工作区内"被拒（实测 DENY）；
- `file -b --mime-type`、pandoc、markitdown 全被拒；
- 技能声明的 CLI 在镜像里不存在。

→ **技能文档在引导智能体走一条必然被拒的路**，每次触发都消耗 3-5 轮试错并最终以道歉收场。

顺带发现（护栏策略倒挂，非本次故障主因）：`python3 <绝对路径>.py` 对 **user 放行、admin 拒绝**——user 白名单是 `python3 *`（任意参数），admin 是 `python3 *.py`（参数必须是工作区内文件）。权限更高的角色反而更严，属策略倒挂。

## 2. 解析质量缺陷（代码审查，本次文件未触发但必然踩）

| 位置 | 缺陷 | 影响 |
|---|---|---|
| `_read_docx` | 只取 `doc.paragraphs`，**表格全部丢弃**；页眉/页脚/文本框/批注/脚注全丢 | 中文业务文档大量内容在表格里 → 读出来"缺了一大块"，智能体以为文档很短 |
| `_read_pptx` | 只取 `shape.has_text_frame`；**不递归 group shapes**，丢表格、备注页（notes_slide）、图表文字 | 组合形状里的文字全丢 |
| `_read_xlsx` | `data_only=True` 取公式**缓存值**；程序生成、从未被 Excel 打开过的文件无缓存 → 全 None；不读图表/批注/合并单元格语义 | 生成的报表读出来是空的 |
| `SUPPORTED_FORMATS` | 声明支持 `.doc/.xls/.ppt`，实际 python-docx/openpyxl/python-pptx **读不了 OLE2 老格式**，异常后落到不存在的 CLI → "解析失败" | 虚假承诺，用户以为支持 |
| `ocr` 分支 | 直接 `return {"error": "OCR 功能需要 markitdown CLI 支持"}` | 图片走 doc_reader 恒失败（应走 view_image） |
| 兜底链 | 依赖镜像里不存在的 CLI（见 1.5） | 兜底 = 无兜底 |
| 参数 | 无分页/页范围/行范围参数；`max_chars=100000` 默认一次性吞 | 大 PDF/Excel 直接爆上下文 |

**关键判断**：docx/pptx/xlsx 本质是 ZIP + XML，用**标准库 `zipfile` + `xml.etree` 零依赖解析**完全可行（docx 的 `word/document.xml`、pptx 的 `ppt/slides/slideN.xml`、xlsx 的 `xl/sharedStrings.xml`）。当前实现把兜底押在不存在的外部 CLI 上，等于没有兜底。**基础能力应该零外部依赖。**

## 3. 修复方案（4 批，未动代码）

### M1 传输层（P0，2 文件）—— 让模型拿到真实路径

- **前端** `client/src/pages/Chat/index.tsx:1469`：
  `source: {url: "file://" + filePath}` → `source: {type:"url", url: "/" + filePath}`
  （与上传附件同构；后端 `_resolve_media_url` 已实测能把它解析成真实绝对路径）
- **后端** `message_processing.py`：
  1. `_resolve_media_url` 不再对 `file://` 短路：剥 scheme 后若 `path` 为空，取 netloc 当文件名，走 media → files → ws media 三级查找；
  2. `_process_single_file_block` 返回空时，`_handle_download_failure` 不要直接吐 `Unknown file source type`，先按 `block.filename` 在 workspace 内兜底查找一次。
- 效果：前端/后端任一侧修好即可通；**两侧都修 = 双保险**（旧前端缓存、第三方渠道、历史消息回放都不再踩）。

### M2 提示词层（P0，1 处）—— 给真实绝对路径

`runner.py` 的 `file_refs` 分支照 `dir_refs` 的既有写法改：

```
AI_Agent技术总结报告.docx (绝对路径: /apps/ai/coapis/workspaces/admin/files/AI_Agent技术总结报告.docx)
```

并在路径不存在时明说："该路径不存在，请用 `glob_search(pattern="*", path="<files根绝对路径>")` 查找" —— 禁止智能体猜路径。

### M3 工具层（P0/P1，1 文件 `doc_reader.py`）—— 基础能力自足

1. **路径解析对齐 read_file**：相对路径依次按 `folder_ref` → `workspace/files/` → `workspace/` 解析；失败时在 workspace 内按文件名 glob，返回**候选绝对路径列表**（"你要的文件在这里：…"），而不是干巴巴一句"文件不存在"。
2. **零依赖兜底**：python-docx/pptx/openpyxl 缺失时，用标准库 `zipfile`+`xml.etree` 直接解析 OOXML（docx/pptx/xlsx），不依赖任何 CLI。
3. **补内容维度**：docx 加表格（`doc.tables`）+ 页眉页脚；pptx 递归 group shapes + 表格 + 备注页；xlsx 公式无缓存时回退给公式串。
4. **老格式诚实化**：`.doc/.xls/.ppt` 明确返回"老格式不支持，请转存为 .docx/.xlsx/.pptx"，从 SUPPORTED_FORMATS 移除（不再虚假承诺）。
5. **图片**：ocr 分支改为提示"请用 view_image 查看图片"。
6. **大文件**：加 `pages`/`sheet`/`max_chars` 范围参数，避免一次吞 10 万字。

### M4 部署 + 技能层（P1）

- `requirements.txt` 取消注释 `python-docx / openpyxl / pymupdf4llm`，与 `pyproject.toml [documents]` 对齐；重建生产镜像后**四格式实测**（docx/pptx/xlsx/pdf 各一份样本）。
- 五个技能文档（docx/pdf/pptx/xlsx/file_reader）改为**优先 `doc_reader`**，删除对 pandoc / markitdown / `file -b` / `python3 -c` 的引导（护栏必拒的引导就是坑智能体）。
- 顺带：护栏 `python3` 策略倒挂（user 宽于 admin）单独决策。
