## 一、实测数据（全部为本次实测，非推断）

### 1.1 后端耗时 vs 每页条数（curl，同一端点 `/api/chats/page`，3 次取稳）

| limit | 耗时 | 响应体积 |
|---|---|---|
| 20 | 12.2 / 12.2 / 12.1 ms | 5740 B |
| 10 | 12.1 / 12.2 / 12.2 ms | 5740 B → 10 条 |
| 5  | 12.8 / 12.2 / 12.1 ms | 2780 B |
| 全量 `/chats` | 12.1 / 12.1 / 12.7 ms | 7653 B（14 条）|

**结论：耗时与 limit 完全无关，恒定 ~12ms。**
原因：`chats.py:601 list_chats_page` 先调 `_build_chat_entries` 构建**全量**条目，
再 `entries[offset:offset+limit]` 切片（:613）。分页只减少**传输体积**，
服务端计算量一条没省。

→ **「20 条降到 10 条」对首屏时间几乎零收益。**

### 1.2 首屏时间线（浏览器实测，admin）

**场景 A：真正首次进入**（新标签，`selectedAgent` 无缓存）

| 时刻 | 事件 |

| 922ms | language / plugins / user-me / preferences |

| 1281–1289ms | 第二批 12 个请求（agents / models / scenes / menus …）|

| **≈2433ms** | 左栏数据就绪 |

**左栏实际渲染：`会话 | 创建新聊天` —— 0 条会话，列表是空的。**
**全程没有发出 `/api/chats/page` 请求。**

**场景 B：第二次进入**（agent 已缓存）

| 时刻 | 事件 |
|---|---|
| 0 → 922ms | JS 启动 |

## 二、问题 1 根因：首次进入左栏慢/空

### 根因 P0-A：agent 未就绪时直接返回空，且无重载触发

`sessionApi/index.ts:1011-1015`
```ts
const agentId = useAgentStore.getState().selectedAgent;
if (!userId || !agentId) {
  return { sessions: [], total: 0, hasMore: false };   // ← 静默返回空
}
```
`selectedAgent` 初值来自 sessionStorage（`agentStore.ts:77` → `getInitialSelectedAgent()`），
新标签页无历史 → **空字符串**。

`ChatSessionDropdown/index.tsx:443-450` 的加载 effect 依赖数组是
`[props.variant, props.open, props.refreshKey, loadSessions]`
—— **不含 `selectedAgent`**。

后果链：左栏挂载 → agentId 空 → 返回空 → **effect 不会因 agent 解析完成而重跑** →
左栏保持空 → 只能等 `Chat/index.tsx:1650 setRefreshKey(+1)`（agent 切换 effect）
间接带动 `refreshKey` 变化才重载。这条链是**串行**的，实测 2.4s。

### 根因 P0-B：首次进入走的是全量端点，分页端点没被用上

场景 A 全程无 `/chats/page`，只有全量 `/api/chats?user_id=…&channel=…`
（`sessionApi/index.ts:941` 的 `getSessionList()` 路径，由 @agentscope-ai/chat 库驱动）。
B5 分页只在 `ChatSessionDropdown` 的 `loadSessions` 里，而它因 P0-A 提前返回了。

### 结论

首屏 1.4–2.4s 的构成里，**后端只占 39–92ms（4%）**。
922ms 的前端启动 + ~360ms 的 auth/agents 串行前置才是主体。
**降每页条数不解决任何问题；修 P0-A 才是治本。**

## 三、问题 2 根因：排序异常（三层，实测坐实）

### 层 1（用户直接感知）：显示口径与排序口径分裂 ★主因

- 排序用 `updated_at`：`chats.py:529 _chat_entry_time` → `updated_at or created_at`
- **行上显示的是 `created_at`**：`ChatSessionDropdown/index.tsx:91`
  `time={formatCreatedAt(session.createdAt ?? null)}`
  `ChatSessionItem/index.tsx:101` tooltip 同样用 `createdAt`

实测左栏渲染顺序 vs 行上显示的时间：

| 行 | 标题 | 行上显示 | 排序键 updated_at |
|---|---|---|---|
| 1 | 请用 execute_shell_command…touch /r | **2026-10-23 14:29:49** | 10-25 00:48（pinned）|
| 2 | New Chat | **2026-10-27 17:08:21** | 10-27 09:08 |
| 3 | 请用 write_file…audit_probe | **2026-10-26 19:53:26** | 10-26 14:54 |
| 4 | 请用 write_file…e2e_check | **2026-10-26 07:56:09** | 10-26 02:56 |
| 5 | 请生成文件 e2e_bar | **2026-10-23 14:20:24** | 10-23 06:20 |

排序键严格倒序（10-25 → 10-27 → 10-26 → 10-26 → 10-23，pinned 置顶）——**逻辑是对的**。
但显示列是 10-23 → 10-27 → 10-26 → 10-26 → 10-23，**视觉上完全乱序**。
用户按显示的时间看，判定"排序有问题"，判定正确。

### 层 2：ISO 字符串字典序比较对格式不一致的时间戳不安全

`chats.py:545-546` 用 `sort(key=_chat_entry_time, reverse=True)`，
`_chat_entry_time` 返回**字符串** → 字典序比较。

实测 dev 16 个 chats.json / 28 个时间戳，存在 **2 种格式**：

| 计数 | 格式 | 样例 |
|---|---|---|
| 27 | `NNNN-NN-NNTNN:NN:NN.NNNNNNZ` | `2026-10-20T05:44:25.638983Z`（微秒+Z）|
| 1 | `NNNN-NN-NNTNN:NN:NNZ` | `2026-10-27T03:00:00Z`（**无微秒**+Z）|

API 输出里还出现第三种 `+00:00` 后缀（`2026-10-27T01:08:21.010881+00:00`）。

字典序陷阱（实测可复现）：
```
"2026-10-27T03:00:00Z"  vs  "2026-10-27T03:00:00.500000Z"
前 19 字符相同 → 第 20 位 'Z'(0x5A) > '.'(0x2E)
→ 无微秒的被判为「更新」，实际 .500000 更晚 → 新条目排到后面
```
同理 `'Z'(0x5A) > '+'(0x2B)` → 带 Z 的恒排在带 +00:00 的前面。

### 层 3：两条加载路径的顺序口径不一致

| 路径 | 端点 | 是否 reverse |
|---|---|---|
| `sessionApi.getSessionList()` :961 | `/api/chats`（全量）| **`.reverse()`** ← 把后端「pinned 优先 + updated 倒序」翻成「pinned 最后 + updated 正序」 |
| `sessionApi.getSessionListPage()` :1031 | `/api/chats/page` | 不 reverse |

两者都写 chat store 的 `sessions`（`Chat/index.tsx:1410` / `:1523`），
左栏读同一个 store。**谁最后写，左栏就是谁的顺序。**
左栏自身有二次排序（`ChatSessionDropdown:362-374`，pinned-first + updated 倒序）掩盖了差异；
台账、搜索弹窗等消费者没有二次排序，会直接暴露倒序。

## 四、方案

### 批次 F1（P0，治本，必做）—— 修排序

| # | 改动 | 位置 |
|---|---|---|
| F1-1 | 排序键改**数值比较**：`datetime.fromisoformat(v.replace('Z','+00:00')).timestamp()`，消除格式敏感 | `chats.py:529-546` |
| F1-2 | 行上显示时间**与排序口径统一**为 `updated_at`（语义 = 最近活跃）；tooltip 同步 | `ChatSessionDropdown:91`、`ChatSessionItem:101` |
| F1-3 | 删除 `getSessionList()` 的 `.reverse()`，两条路径统一为「后端顺序即显示顺序」 | `sessionApi/index.ts:961` |

> F1-2 需产品拍板：行上时间显示「最近活跃(updated)」还是「创建时间(created)」。
> 若坚持显示 created，则排序也必须按 created 排，否则视觉永远乱。

### 批次 F2（P0，治本，必做）—— 修首次进入

| # | 改动 | 位置 |
|---|---|---|
| F2-1 | 左栏加载 effect 依赖数组**加入 `selectedAgent`**，agent 就绪即刻重载 | `ChatSessionDropdown:443` |
| F2-2 | `getSessionListPage` 在 agentId 空时**不静默返回空**，改为解析默认 agent 后重试（前端已有 `/api/agents` 数据可用） | `sessionApi/index.ts:1011` |
| F2-3 | 左栏空态加骨架屏（区分「加载中」与「真没有」） | `ChatSessionDropdown:491-503` |

### 批次 F3（可选）—— 每页条数与「今日」分组

实测已证明：**降 limit 对首屏无收益**（后端 12ms 恒定）。
降 limit 唯一收益是少渲染 ~7 行 DOM，量级可忽略。

若要做「按时间显示今日」，三个候选：

| 方案 | 描述 | 代价 | 评价 |
|---|---|---|---|
| **G1 纯前端分组** | 后端照旧返回一页；前端按日期分组「今日 / 昨日 / 更早」，默认展开今日，底部「查看更多」翻页 | 仅前端，1 人日 | **推荐**。零后端风险，分页语义不变 |
| G2 后端加 `since` 参数 | `/chats/page?since=today` 取今日，不足 N 条再补最近一周 | 后端 + 前端，2 人日 | 精确，但 `_build_chat_entries` 仍全量构建，无性能收益 |
| G3 降 limit 到 10 + 加载更多 | 现状已有「加载更多」 | 1 行 | 实测无收益，不建议单独做 |

「今日无会话时显示什么」需拍板（三选一）：
- (a) 显示空态 + 「最近一周」按钮
- (b) 自动补最近 1 条（今日区显示「今日无会话，最近一条：…」）
- (c) 今日区缺失，直接显示最近一周
