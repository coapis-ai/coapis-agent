## 〇、一句话结论

方案的**方向与验收标准是对的**（口径统一、一条标准链、小流量起步、11 条"怎么算好"全部可采纳），
但它的**基线数据取自企业版生产库（4890 / PostgreSQL）**，不是社区版；
并且把问题判成"四条断路"，实测是 **三个真凶 + 十条断路**——
其中最要命的三件事方案里一个字没提：

1. **仓库里有三套互不兼容的 `MemoryEntry`**，台账写入用第一套的调用方式去构造第二/三套没有的字段 → 写入第一行就 `TypeError`（这才是"探针必崩"的真身）；
2. **台账目录在镜像里（`/app/coapis/foundation/knowledge_base`），不是宿主挂载卷** → 容器重建即清零；方案说"宿主机绑定挂载，升级镜像不会丢"，实测**不成立**；
3. **聊天注入的"已批准经验/跨智能体全局基础层"两个数据源路径 = `Path(os.environ.get("COAPIS_DATA_DIR", "/data"))/...`，而 dev 与企业生产容器里 `COAPIS_DATA_DIR` 都没设置**（实测 `printenv` 空）→ 回落到 `/data`，而容器内 `/data` **不存在** → 这两条注入通道永久为空（`react_agent.py:2858-2861`、`:2927-2932`）。

同时方案**低估了已有资产**（复用现成可省约 40% 工作量），也**低估了自动化已跑出的脏数据**
（`knowledge_flow/professional` 里已有 **732 条自动晋升知识**，其中 29 条 content 为空壳、优先级恒 0.9–1.0、复用次数全 0、重复未去重、无人审核）。

### B. 三套 `MemoryEntry` 语义分裂（写入必崩的真身）

- `foundation/memory_entry.py`：`priority_score / access_count / compute_priority() / user_confirmed / tags / source_agent|source_user|source_session`，**无 scope/importance/title/dedup_key/source/user_id/priority**
- `foundation/memory_repository.py`：`scope / importance / title / dedup_key / agent_id / workspace_id / deleted_at`，**无 access_count/priority_score**
- `evolution/memory_capacity.py`：第三套
- `foundation_manager.py` 全部按"旧 API"调用 → 写入崩、检索崩、`add_memory` 不存在、`quota.can_add` 不存在（`MemoryQuota` 只有 `is_full/can_inject/has_space/is_user_entries_full/...`）

**好消息**：`memory_entry.py:88 compute_priority()` 已实现"访问频率 30% + 用户确认 25% + 时效 20% + 跨会话复用 15% + 类型权重 10%"——**方案 P0-4 要的"合并计分"公式现成就在代码里**，只是没有数据源喂它（DB 缺 `access_count`）。

### C. 首轮注入不受配额裁剪

`build_context(is_initial=True)` 直接返回核心层+思考层全文（2687 字节），核心层配额是 2000（`MEMORY_INJECT_LIMIT_CORE=20000×10%`）→ **出厂层超预算不裁剪**，台账一进来就会把预算吃光后仍照灌。方案 P0-2 的"预算"必须在初轮分支也生效。

## 五·五、晋升全自动铁律（2026-11-07 小蜜蜂再次明确，本轮据此更正方案）

**小蜜蜂的要求（反复明确过）：晋升全自动，不要人工审核。** 上一版总结里"入库前人工审"
与 D3"逐条点"是蜜总裁写歪了，现按铁律改回。

**铁律口径（唯一口径，全项目以此为准）**

| 环节 | 谁做 | 说明 |
|---|---|---|
| 准入（写不写进台账） | **机器** | 阈值尺子：`importance≥阈值` 且 `复用次数≥阈值` 且 非空壳 且 去重（重复只合并计数不新增） |

| 淘汰（降级/归档） | **机器** | 长期零命中/零采纳 → 自动降级、改名归档（`.archived`，可恢复，不物理删） |
| 治理（撤销/钉住/关停） | **人，事后** | 只有三个动作：**撤销**一条（下线）、**钉住**一条（不被淘汰）、**关停**一条（永不晋升）。**没有任何"事前审批"** |

**为什么人工审核必须删掉，而不是"建好它"（实测依据）**
1. 待审队列是**进程内存列表**：`evolution_engine.py:240 _pending_experiences`、
   `knowledge_flow.py:_flow_queue`、`backend_review.py:106 _pending_reviews` → **重启即清空**，
   人工审核在技术上就立不住；
2. "审核通过"按钮调的方法**不存在**（`FoundationManager` 无 `add_memory`，`evolution.py:335`）
   → 服务端必 500，这条路本来就是死路；
3. 上一版方案第三节"不能做"里已写明 **❌ 人工审核工作流（已定全自动，不建审核队列）**，
   D3 与总结①与之自相矛盾 → 以铁律为准。

**界面口径随之改变**：治理页"待晋升审核"页签 → 改为**只读「晋升记录」**
