## 〇、一句话结论（必须先看的架构变更）

**真相层不是"文件台账"，是已经在工作的 SQLite `memories` 表。**
dev 实测（`/apps/ai/coapis/system/coapis.db`，宿主卷、容器重建不丢）：

|---|---|---|

**正确做法：数据库做真相，文件层降级为"导出投影"（幂等重建，只给智能体发现/注入/用户下载用）。**

## 二、架构决定（本轮唯一需要拍板的大方向）

```
真相层  : SQLite memories 表（scope=user|agent|global，importance，dedup_key，deleted_at）
晋升层  : 时间线 → memories（已实现的 cron，参数接配置）
投影层  : 导出 md + index.json（幂等重建，落 WORKING_DIR/foundation/knowledge_base）
发现层  : kb_adapter 读投影目录（统一尺子 score_match，已注册）
注入层  : 开局 top-N 相关记忆（score_match+importance，配额裁剪）→ core.py:903
聊天层  : memory_search 工具（已有）+ "记下来"按钮（新）+ 引用溯源卡片（复用）
治理层  : 现有进化页加"记忆与晋升"只读区块 + 撤销按钮（软删）
```

**为什么这样最省：** 幂等导出 ⇒ 不存在"索引/文件失配"；DB 在宿主卷 ⇒ 不存在"重建清零"；
单一写入模型（`memory_repository.MemoryEntry`）⇒ 三套模型只在写入处收敛，不动注入/进化内部；
软删 ⇒ 归档与撤销零成本。
