# 知识库顶层设计（检索服务层 + 独立入口）— 定稿 v1.0

> 本文件是「知识库」作为企业版新增能力的**能力契约与边界定义**。目标是让聊天/工具等外部消费者通过最小依赖调用知识库，而不感知内部实现。所有决策已收敛于本文档末尾的检索服务层链路。

---

## 一、定位与边界（不可乱）

- **独立入口**：知识库是自有能力模块，有独立的「顶层设计与逻辑」。**聊天/工具不直接操作知识库的内部数据结构**。
- **最小耦合契约**：外部只通过一个统一的检索接口调用，按"输入→输出结构"交互。内部实现换掉（如向量换成 BM25）不影响任何消费者——这是隔离的核心价值。
- **能力注册表**：知识库对外暴露的能力集中在一张「能力清单」里（见第四节），新增功能只需往这张表登记一项契约，无需重写现有逻辑、也无需改动其他模块的调用方式。**这就是"灵活/可扩展"的实现机制**。

---

## 二、检索服务层链路（定稿）

### 2.1 默认行为（正常搜索 = 不加权）

用户决策：**「正常搜索基础权重均为 0」** → 即**默认不做跨库加权**，退化为纯 score 全局排序。
> 技术澄清：若加权为乘性因子，"权重=0"会把分数全清成 0；因此此处指 **「额外均衡增量为 0 / 不施加跨库保护」**。

链路（单条）：

```
query → [松弛召回] → [归一化 min_score] → [全局 score 截断 topk] → per_kb_stats(可观测)
```

1. **松弛召回**：每个知识库在 `topk × factor`（factor=2，可调）范围内先取候选，避免单库贡献过少导致全局不足。
2. **归一化 + min_score 过滤**：按各库的 score 分布做归一化后统一阈值过滤；默认 min_score = 0（即不过滤），特殊场景可上调。
3. **全局 score 截断 topk**：**最终只返回全局前 `topk` 条，与知识库数量无关**。彻底解决「10个库 × topk=5 → 返回50条」的爆炸问题——这是靠**全局截断**而非加权解决的。
4. **per_kb_stats（可观测性）**：仍输出每个库贡献的数量。**即使默认不加权也要暴露这个统计**，用于观察是否存在单库主导现象；一旦观察到异常，再单独对那个库做归一化或启用加权——把"复杂处理"藏在可选开关里。

### 2.2 可选行为（特殊场景才启用）

当 per_kb_stats 显示某大库明显霸榜、需要刻意保多样性时：
- **算法 A**（无参数，零配置）：`score / sqrt(count)` —— count 越大惩罚越重，天然抑制内容多的大库。
- **算法 B**（可配因子 α）：`(1−α)·normalized + α·(1/count)`；默认 α=0 即退化为纯 score 排序，需要时才填 α。

两种算法都是"锦上添花"的可选增强，**不改变默认链路、不影响现有消费者**。

### 2.3 topk / factor 的来源
- `topk`：知识库配置项（每个库可不同），缺省走全局默认值；聊天/工具调用时可覆盖为特定值。
- `factor`：检索服务内部参数，不在对外契约里暴露给用户——用户无需关心召回数量细节。

## 三、能力契约 / 统一检索接口

知识库只向外部暴露**一个**核心检索方法（默认多库搜索），按签名区分行为：**不要为不同场景写多个 search_* 方法**。

```
search(query, topk=None, factor=2.0, min_score=0.0) -> { results: [...], per_kb_stats: {...} }
```

- **参数即能力**：`topk`/`factor`/`min_score` 都是可选，缺省 = 默认多库搜索。指定范围、单库等"特殊需求"通过这几个参数表达，而不是新增方法签名。
- **输出结构稳定**：
  - `results`：全局 topk 片段列表，每条带 `{kb_id, kb_name, score, content, source_title}`（source_title = 来源文档标题）。
  - `per_kb_stats`：每个库贡献数 + 是否触发加权。用于可观测与调试，**不强制外部消费**。

---

## 四、能力注册表（可扩展性的落地机制）

知识库对外暴露的能力登记在一张统一清单里。**新增任何功能，只需往这张表加一行契约**，无需重写现有逻辑：

| 能力 | 入口/方法 | 说明 |
|------|-----------|------|
| 多库检索（默认） | `search()` | 全局 topk、per_kb_stats；聊天/工具的唯一调用点 |
| 单库检索 | `search(kb_id=...)` | 同一方法的 kb_id 参数，非独立方法 |
| 知识库列表/详情 | `/kb/*` REST | 管理侧接口，与运行时检索解耦 |

> **扩展原则**：外部（聊天）要调用新能力时，只需在注册表登记一项契约；现有消费者零改动。这就是"不写死、可扩展"的本质——靠**统一契约 + 参数化行为**实现，而非为每个场景复制一份逻辑。

---

## 五、与聊天/工具的集成边界（最小依赖）

- **外部只持有「调用能力」的引用**：通过注册表拿到 `search` 方法句柄并按签名传参。**不 import 知识库内部模块**。
- **检索结果结构化回灌**：聊天消费的是 `results` 这个稳定结构，无论底层是向量还是 BM25。
- **无工具/技能依赖（默认）**：确定性 RAG，不需要额外 tool/skill；特殊场景才需要时再登记一个新能力项即可。

---

## 六、最终分层交付清单（按架构层而非 P0/P1）

| 层 | 交付内容 | 验收标准 |
|----|----------|----------|
| **检索服务层** | `search()`：松弛召回→归一化→全局 topk 截断；默认不加权(α=0)；per_kb_stats 可观测；加权为可选开关（算法 A/B） | 10库×topk5 → 仍返回全局前5，无爆炸 |
| **能力契约层** | 统一 `search(query, topk, factor, min_score)` + per_kb_stats 输出结构 | 外部按签名调用即可，无需感知内部实现 |
| **能力注册表** | 登记检索/列表等对外能力清单；新增功能只加一行契约 | 消费者零改动扩展新能力 |
| **独立入口** | /kb/* REST（管理侧）与运行时 search() 解耦 | 知识库逻辑自成体系，不依赖聊天实现 |
