## 三、用户点名的三个重点：核实结果与缺口

### 重点①「优化聊天中任务决策」——方案覆盖良好，但根因比方案写的更尖锐

实证链（技能首轮流失的真根因）：

- `agents/utils/skill_selector.py:474-481`：
  ```
  # If we're in an async context, skip LLM classification
  # (This shouldn't happen in reply() flow, but guard against it)
  try:
      asyncio.get_running_loop()
      return []          # ← 异步上下文直接返回空
  except RuntimeError:
      pass
  ```
  注释断言"reply() 流程里不会发生"——**但 `reply()` 就是 `async def`（react_agent.py:4166）**，`get_running_loop()` 必然成功 → **`select_skills_by_llm` 在正常聊天流里永远返回空，LLM 技能分类从不执行**。
- `react_agent.py:1959-1988` 的 Phase 1/2：Phase 1 关键词命中即跳过；**Phase 2（LLM 分类）只在关键词全部落空时才跑**——即"新任务/新表述"这一最典型场景；且用线程池 + 嵌套事件循环**同步阻塞 5 秒**。
- `_load_on_demand_skills()`(react_agent.py:2019-2034) 只做关键词匹配，无 LLM、无缓存。

→ 结论：**"首轮流失"不是策略问题，是一处死分支 + 一处线程池兜底。** 修这两处的收益大于新建整套 P5。

### 重点②「结合执行过程进行过程决策优化」——方案只写了"事前"，缺"事中"

方案有 P2（计划审查，事前）与 P3（工具闸门，逐次），**没有"计划执行中随进度改判"**。

现成挂载点：`HookPhase.PRE_ACT`（每次工具调用前）、`HookPhase.POST_ACT`（之后）、`plan/broadcast.py`（计划状态广播，已在 `_register_hooks` 挂载）。

→ 需补：**步骤级复判**——每完成一步，对"剩余步骤 + 已产生事实"重新判级（继续/改道/升级模型/请求确认），产出写台账。这是"过程决策优化"的落点，方案缺失。

### 重点③「聊天中优化用户信息提示、用户上传文件」——**方案完全没覆盖**

现状实证：

- 上传接口已会话化：`app/routers/files.py:287-300`（`chat_id`/`session_id` 表单字段 + 会话目录解析）、`:375-383`（上传即登记台账，source=upload, status=draft）
- 前端已 chat_id 感知：`client/src/pages/Chat/index.tsx:110-113`（上传前同步 chatId→sessionApi）、`:1146-1152`（上传带 chat_id）、`:1169`（失败提示）；上限 10MB（`:1162`）
- 文件引用注入提示词：`app/runner/runner.py:2100-2175`（相对路径→工作区绝对路径解析后注入）
- 用户信息注入提示词：`agents/prompt.py`（按 username/agent_id 组装，`:623` 取模亦按 username）

缺口（方案 P1 输入声明了"附件存在性"，但**没有任何岗位消费它**）：

1. 附件的**类型/大小/解析状态**未进入判断输入——有 pptx 却没告诉 P2"计划里必须有解析步骤"，是"计划落空"的主要来源之一
2. 上传文件的**解析失败/降级**未纳入台账与判据（解析超时/超阈值的降级建议逻辑在文档解析链路里存在，但与判断中枢脱钩）
3. 用户信息（角色/权限/偏好/时区）未作为 P1/P3 输入——权限边界判断目前只在护栏硬规则里，判断中枢不参与
4. 前端上传体验缺口：无粘贴上传、无拖拽全局提示、无上传进度条、无重复上传识别、无"该文件已在本会话"提示

→ 必须在方案里补一节 **「P1 输入面扩展：附件与用户上下文」**，并把"附件清单 + 解析状态"列为 P2 计划审查的强制输入项。

## 四、方案的其他缺口（核实中发现）

**G1 知识库前端有壳、后端无路由。**
`client/src/api/modules/knowledge.ts` 调用 `/knowledge/bases|search|stats|tags`；`app/routers/__init__.py` 注册的 26 个路由里**没有 knowledge**；`foundation/knowledge_base/` 只是 markdown 目录（general/system），无检索服务；`agents/resources/kb_adapter.py:1` 是适配器。**P5 的"知识库检索"当前无处可判**——需先补后端路由与检索实现。

**G2 P3"只加严"与现有降级规则冲突未定义。**
`security/tool_guard/unified_engine.py:139 _apply_demotion_rules()` 会**放宽**动作。方案规定 P3 只加严，但没写二者优先级——不定义则"加严"会被现有降级规则抵消。

**G3 治理面板落地清单缺"菜单标签"。**
菜单由数据库标签驱动（`app/routers/menus.py:42` → `TagService.list_menu_tags()`），前端动态渲染。新增面板需要：后端 router 文件 + `include_router` + **菜单标签入库** + 前端页面 + 4 语言键。方案只写了前两项。

**G4 方案未声明复用 HookPhase / resolve_chat_model_slot / shadow 三态。**
不复用的后果正是方案自己反对的"多份副本"——会出现第二套钩子、第二套取模、第二套影子统计。

**G5 槽位命名需按真实枚举修正。**
新增应为第 6 类 `judgment`，与 chat/embedding/rerank/audio/vision 并列；方案文案里的"推理"槽位不存在，需删。

**G6 台账"状态字段必须持久化"应写成硬约束而非"修复问题"。**
现台账已入库带 status；真正的风险是**新建判断台账时重蹈字段丢失覆辙**（provider.py:542 注释、load_bindings 500 两次先例）。建议列为验收红线：新表所有字段 `nullable=False` + `server_default`，序列化用显式列举（仿 `DefaultModelsConfig.to_dict` 的显式列举写法）。
