## 一、缺陷清单（按严重度，全部带行号证据）

### P0-1 技能加载层 Stage2 永久失效（传参契约错配）

- 证据：`agents/utils/intent_classifier.py:155-158` 签名 `(user_message, skill_summaries, scope=None)`；
  调用方 `agents/utils/skill_selector.py:547`、`:586`、`app/routers/skills.py:2409` 传 `timeout=timeout`。
- 容器内运行时实测：`TypeError: classify_intent_llm() got an unexpected keyword argument 'timeout'`，
  被调用方宽 `except Exception` 吞掉 → 静默返回 `[]`。
- 影响：加载层"意图驱动技能装载"**从未成功过一次**；技能岗真判 39 次仅 3 次命中技能。
- 修复：三处调用去掉 `timeout=`，超时由网关尺子统一管（**逻辑归一，不在调用方私自定尺子**）。
- 工作量 0.2 人日；风险 低。

### P0-2 软超时"先判罪后补判"→ 把成功判官推上熔断

- 证据：`decision/gateway.py:673-691` 软超时即 `breaker.record_failure` + 写 `timeout` 台账行，
  随后 `_judge_bg_complete`（`:770-845`）后台判完**再写一行 `llm` 台账 + `record_success`**。
- 实测：台账中**一次判两次记账 16 对**（timeout 行 + 迟到真判行）；reason 含熔断中 24 行。
- 后果：判官真判 p50 5997ms > 软阈 2s → **每次真判都先贡献一次 failure**，
  `breaker_failure_threshold=5` → 熔断被"慢而成功"的判官反复推开 → 后续判断全 5ms 假弃权。
- 修复（逻辑级，三件）：
  1. 软超时**不计熔断失败**（新增中性事件 `timeout_soft`，只有硬超时/异常/无模型计失败）；
  2. 台账**一次判只记一行**（迟到补判用 UPDATE 覆盖原行，不 INSERT 第二行）；
  3. 软阈与真实耗时匹配：分岗软阈（判档 4s / 技能 6s / 工具 6s / 验收 12s），
     并把主链**同步 await 岗改异步**（见 P1-1）。
- 工作量 1.5 人日；风险 中（改台账记账口径，需同步预检尺子）。

### P0-3 兜底技能硬灌 8 个（无关技能污染上下文）

- 证据：`skills/manager.py:726-727`（`if scores: 前8` / `else: _fallback_skills`），
  `FALLBACK_SKILL_CAP = 8`（`:290`）。
- 实测：`你好` → 8 个；`把这段中文翻译成英文` → 8 个；`每天9点跑评测` → 8 个。
- 修复：兜底只给 `always_load` + 至多 1 个（按会话近邻），无匹配就**明说无匹配**；
  命中数加**上限 3 + 最低分数门槛 4**（Tier3 单二元组命中 3 分不足以入载）。
- 工作量 0.5 人日；风险 低（行为变化需回归验证）。

### P0-4 幽灵映射 51%

- 证据：`skills/manager.py:478` `_TRIGGER_MAP`，实测 70 条目标中 36 条指向不存在技能；
  `:699-706` 命中后 `_find_skill_by_normalized_name` 返回 None → **静默跳过**。
- 修复：① 启动时校验映射目标，幽灵条目**告警清单**输出（不再静默）；
  ② 删除/改写幽灵条目（浏览器类映射到真实在池技能或移除）；
  ③ 校验进自检闸门（导入期自检，与既有 dev 导入自检同一条路）。
- 工作量 0.5 人日；风险 低。

### P1-1 主链同步 await 判官（前摇）

- 证据：`agents/react_agent.py:2042` 技能岗 `await self._llm_classify_skills(...)`
  （仅关键词全空时触发）；`:4616` 判档 `await classifier.classify_smart(text)`（`_maybe_arm_plan`，reply 内）。
- 实测：判档真判 avg 2841ms/max 8852ms；技能岗 avg 5321ms/max 12820ms；timeout 行 max 15001ms。
- 修复（逻辑级，不改判官耗时）：
  1. **判档与技能判并行发起**（同一轮同一次预判断，两者共享一次判官往返）→ 前摇
     `2.8+5.3 = 8.1s` → 约 **6s**（取较大者）；
  2. **上一轮预判/预取**：reply 开始时并行发起判档与技能判，主链只在需要时 `await` 已发起的 future
     （最坏仍受软阈封顶，正常路径几乎 0 前摇）；
  3. 复用：判档已给出 L0 且关键词层已命中技能 → **跳过技能判官**（现逻辑已部分短路，补判档短路）。
- 工作量 2 人日；风险 中（涉及 reply 时序，需回归 + 无模型冒烟）。

### P1-2 计划审查提示未打 HINT 标记 → 永久污染历史

- 证据：`agents/react_agent.py:1182` `await self.memory.add(Msg(...))` **无 `marks=`**；
  对照 `:3656`（advisor）、`:4624`（计划骨架）、`:4247`（工具门禁）均带 `marks=_MemoryMark.HINT`。
  上游 `ReActAgent` 依赖 `delete_by_mark(mark=_MemoryMark.HINT)` 清理临时提示。
- 后果：计划审查结论**永不清理**，逐轮堆积在历史里（并进入压缩），且与"下一轮生效一次"的设计不符。
- 修复：加 `marks=_MemoryMark.HINT`（1 行）。
- 工作量 0.1 人日；风险 低。

### P1-3 场景核心技能全文注入无字节上限

- 证据：`agents/react_agent.py:317` `MAX_SCENE_CORE_SKILLS = 5`（按**个数**封顶，无体积闸）；
  实测全池 SKILL.md 182.8KB（≈117K tokens），**最大 5 个合计 96.8KB ≈ 62K tokens**。
- 后果：场景表一旦配了大技能（co-agent 25KB、oa 22KB、make_plan 19KB…）→ 单请求注入数万 token。
- 修复：核心注入加**总字节闸**（建议 8KB，超限只注入索引行 + 触发句），并输出体积遥测到台账。
- 工作量 0.5 人日；风险 低。

### P1-4 Tier1 子串匹配无词边界 + 短关键词泛滥

- 证据：`skills/manager.py:694` `kw_low in query_lower`；实测池内 **≤2 字符关键词 59 个**
  （安装/配置/帮助/优势/研究/发布/邮件…）；`分析这个数据文件` 命中 9 个（`数据` 6 次累加）。
- 修复：短词（<3 字符）不参与 Tier1 计分（移入 Tier3）；Tier1 命中按**去重技能计分**（同 kw 多次出现不累加）；
  命中数上限 3。
- 工作量 0.5 人日；风险 中（命中率变化需 A/B 复测）。

### P2-1 闭环率低的真实原因（更正旧结论）

- 证据：`decision/hub_acceptance.py:256-290` 回填目标**设计为** `source='plan_gate'` 行
  （按 `chat_id(+turn)` 定位）。→ 23 行 outcome 全打在判档行是**设计如此，不是 bug**。
- 真因：判档行 **chat_id 空 33%、turn=0 41%**（均为 10-29/10-31 时代与身份缺失路径）→ 定位不到行 → 闭环失败。
  近 24h 数据身份 100% 齐全（turn=1、chat 齐全）→ 该链路已通。
- 剩余：判档在身份缺失入口（A2A/cron/无会话上下文）仍写空身份 → 空身份行**不该进台账**（记 `origin=no_identity` 单独口径）。
- 工作量 0.3 人日；风险 低。

### P2-2 事中改道/计划审查 0 真判 —— 不是断线，是**门槛+流量**

- 证据：`decision/hub_advisor.py:64-71`（`iters>=8` 且 `(iters-8)%6==0` → 40 迭代最多 6 次）。
- 台账仅 7 行：dev 缺少 ≥8 次工具迭代的长任务。**接线完好**。
- 建议：加"长任务才判"的显式开关与台账标注（`long_task=true`），并把门槛做成配置；
  评测集里补长任务用例（否则永远无法验证这两个岗）。
- 工作量 0.3 人日；风险 低。

### P2-3 台账口径混算（真判率被虚高/虚低）

- 证据：`hit_layer` 分布 llm 81 / cache 2 / **rule 7**；旧口径把 rule 计入"真判"。
- 修复：预检脚本分三层口径——`判官真判(llm+cache)`、`规则直判(rule)`、`弃权/损耗`，
  并在报表里分开；迟到补判合并为一行后不再重复计数。
- 工作量 0.3 人日；风险 低。

## 二、"判得准 / 装得省 / 用得对 / 可度量"四条效能线

**判得准**：P0-1（Stage2 复活）+ P0-4（幽灵映射）+ P1-4（匹配阈值）+ 判档结论复用给技能岗。
**装得省**：P0-3（兜底 8→1）+ P1-3（核心注入字节闸）+ 命中上限 3 + 索引 query 态（实测 74 字）。
**用得对**：逐条消息指定技能（P1-5，见下）+ 技能与判官协同回执（判官预激活 → 装载 → 执行结果回台账）。
**可度量**：P0-2 单行记账 + P2-3 三层口径 + 迟到真判计数 + 前摇 ms 遥测。

### P1-5 逐条消息指定技能（小蜜蜂提过，链路已核实畅通）

- 现状：`app/routers/console.py:293` 入参是自由 `Dict`（含 `biz_params`），**无技能字段**；
  前端发送不带技能；装载层 `_load_on_demand_skills` 不尊重指定。
- 最小改动集：① 前端选择器 → `payload.biz_params.skills=[...]`；② `console.py` 提取并透传；
  ③ `scene/resolve.py` 写入本轮上下文；④ `_load_on_demand_skills` 顶部尊重指定
  （指定即装载 + **跳过判官兜底**，省一次判官往返）。
- 工作量 1.5 人日；风险 中（涉及前端 UI 与权限校验：只能选自己可见技能）。

## 四、验收标准（判官模型未接入时即可跑通）

1. 无模型 30 项探测全绿，主链最坏前摇 ≤ 2.1s（现状 6s+）。
2. 台账：一次判**只一行**；`timeout_soft` 不再计熔断失败；三层口径报表分开。
3. 技能：`你好` 类请求兜底 ≤2 个技能；命中 ≤3；幽灵映射告警清单为 0 条（清理后）。
4. 场景核心注入体积 ≤8KB 并可在台账查到体积。
5. 计划审查/advisor/工具门禁提示均带 HINT 标记，回复后能被 `delete_by_mark` 清空。
6. 指定技能：前端勾选 → 后端装载 → 台账 `origin=user_picked` 且跳过判官。
7. 全量测试绿；dev 部署；生产不动。

## 五、需要小蜜蜂拍板

- **D1 软超时是否计熔断失败**（推荐：**不计**，只计硬超时/异常/无模型）。
- **D2 台账单行记账**（推荐：**UPDATE 覆盖**，迟到真判改写原行 → 口径干净）。
- **D3 主链是否允许"异步预判"**（推荐：**允许**，reply 开始并行发起，需要时 await future；
  代价：极短请求也用一次判官预算格）。
- **D4 分岗软阈**（推荐：判档 4s / 技能 6s / 工具 6s / 验收 12s，写进配置不写死）。
- **D5 技能兜底策略**（推荐：`always_load` + ≤1；命中上限 3，最低分数门槛 4）。
- **D6 指定技能 UI**（推荐：聊天输入区"本轮技能"多选，仅列自己可见技能，上限 3）。
- **D7 空身份判断是否入台账**（推荐：入台账但单独 `origin=no_identity`，不计入真判率分母）。
