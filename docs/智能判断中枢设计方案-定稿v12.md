## 1. 设计目标与原则

**目标（按优先级）**

1. **判断权归位** — 判断由「判断能力」决定，不由代码分支决定。
2. **零感知延迟** — 判断不进入用户可感知延迟。
3. **可持续进化** — 判据成为可版本化、可审批、可回滚的资产。
4. **缺位可用** — 没有任何决策模型时，系统行为不劣化、不中断。
5. **可度量** — 每一次判断都有台账，可复盘、可校准。
6. **分层暴露** — 默认极简，高级能力按需可达。

**硬原则（不可妥协）**

- **P1 唯一入口**：全系统只允许一个地方决定「用哪个模型做判断」。任何模块不得自行取模型。
- **P2 永不兜底抓第一个模型**：无可用判断能力时明确返回「无判断」，由调用方走规则路径。
- **P3 判断只加严不放宽**：判官只能把「放行」改成「需确认」，绝不能把安全规则判定的「拦截」改成「放行」。
- **P4 关键路径零同步模型调用**：用户消息进入 → 首 token 产出之间，禁止任何同步模型判断。
- **P5 自动生效必带影子**：任何自动生效的判据变更，必须先经影子双跑验收；红线类永不自动。
- **P6 不新增用户可见配置**：判断能力复用现有模型配置体系，不引入新环境变量、不向普通用户暴露参数。
- **P7 复用优先**：台账、版本、审批、效果评估、回滚全部复用社区版既有机制，企业版只做存储替换与扩展视图。

## 2. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│ L4 治理与可观测  Governance                                   │
│   判断台账 · 降级可见 · 影子对比 · 预算看板 · 校准建议        │
├─────────────────────────────────────────────────────────────┤
│ L3 判断资产  Judgment Assets                                  │
│   判据技能包（版本/审批/效果/回滚）· 三档生效 · 阈值外置      │
├─────────────────────────────────────────────────────────────┤
│ L2 判断岗位  Judgment Posts（六岗位 = 六结合点）              │
│   入口路由 · 计划审查 · 执行闸门 · 完成验收 · 技能优选 · 成本分层│
├─────────────────────────────────────────────────────────────┤
│ L1 判断总线  Judgment Bus（全系统唯一取模入口）               │
│   ask() · 四级回落链 · 熔断 · 缓存 · 预算配额 · 批量合并      │
├─────────────────────────────────────────────────────────────┤
│ L0 判断能力  Judgment Capability                              │
│   判断槽位 · 能力探测 · 外部决策API / 本地量化模型 / 判别模式  │
└─────────────────────────────────────────────────────────────┘
```

**依赖方向**：L2 → L1 → L0，单向。L3 为 L2 提供判据，L4 消费 L1/L2 产生的记录。业务代码只允许调用 L2 岗位，不允许直接触达 L1/L0。

**与现有系统的关系**：判断中枢是**新增的横切层**，不改动社区版对话主流程的结构，只在既有决策点「换脑子」——把原来写死的分支替换为对岗位的调用。企业版侧只做两件事：台账落 PostgreSQL、判据技能包落企业知识库检索增强，不新增平行实现。

## 3. 核心组件设计

### 3.1 L0 判断能力层

**判断槽位**：在模型配置体系中新增第 6 类槽位 `judgment`，与现有五类槽位（对话/推理/嵌入/重排/视觉）平级。槽位是**登记**，不是**绑定**——槽位只声明「哪个模型被指定为判断能力」，具体谁在什么时候用它，由 L1 总线决定。

**能力画像（Capability Descriptor）**：运行时探测产出，字段：

| 字段 | 含义 |
|---|---|
| `available` | 是否可用（探测通过） |
| `protocol` | `openai-chat` / `openai-completion` / `native-prompt`（原生提示协议，支持一次前向多问题） |
| `latency_p95_ms` | 实测延迟分位 |
| `supports_json_schema` | 能否强制结构化输出 |
| `max_batch_questions` | 一次前向可合并的判据数 |
| `cost_per_1k` | 单价，用于成本分层 |

**四级能力来源（优先级从高到低）**

1. **外部决策 API** — 专用判别式服务（如百炼决策模型）。优势：不占本机显存、支持一次前向多问题。
2. **本地量化判别模型** — 小参数量判别式模型（0.4B～0.8B 级，Q4 量化，约 3GB 显存），以 OpenAI 兼容端点自托管。优势：零调用成本、数据不出域。
3. **生成模型判别模式** — 复用现有对话模型，强制结构化输出 + 极短提示 + 独立小预算上下文。作为过渡形态，能力画像标记 `degraded=true`。
4. **规则引擎** — 现有关键词/正则/启发式判据。永久兜底，永不下线。

**缺位三层保障**（对应需求 4）

- 第一层：槽位未配置 → 总线直接返回「无判断」，调用方走规则路径（零额外开销）。
- 第二层：槽位配置了但探测失败 → 熔断打开，冷却期内直接走规则，冷却结束探针恢复。
- 第三层：探针成功但单次调用失败 → 该次降级为规则，台账记录降级原因。

三层都不需要用户干预，也不产生用户可见报错。

### 3.2 L1 判断总线

**唯一公开接口**（全系统只此一个）：

```
ask(req: JudgmentRequest) -> JudgmentOutcome
```

**JudgmentRequest**：`post`（岗位）、`criteria_id`（判据）、`mode`（`classify`/`score`/`select`/`gate`）、`input`（结构化输入）、`options`（候选集，用于选择型判断）、`deadline_ms`（该岗位预算）、`sync_hint`（调用方声明是否可异步）、`session_ref`。

**JudgmentOutcome**：`decision`（判定结果）、`confidence`、`source`（`model`/`rule`/`cache`/`default`）、`degraded`（是否降级及原因）、`criteria_version`、`latency_ms`、`cost`、`judgment_id`（台账主键）。

**四级回落链**（P1/P2 的落地）：

```
判断槽（能力画像可用）
  → 对话槽（仅当画像允许判别模式，且该岗位预算充足）
    → 规则引擎
      → 保守默认（岗位各自的「无判断默认值」）
```

链上每一级都写入台账 `source` 字段，可统计「判断覆盖率」「降级率」。彻底移除任何「抓第一个可用模型」的兜底逻辑。

**熔断器**：进程级，连续 3 次调用失败 → 打开 600 秒 → 期间直接走规则 → 到期发 2 秒探针。参数内置，不进配置文件，不给界面。

**判断缓存**：键 = `(criteria_id, criteria_version, input_fingerprint)`；TTL 300 秒；容量上限 + LRU 淘汰（避免无界增长）；命中直接返回并标 `source=cache`。缓存对「选择型」与「分类型」判断收益最大。

**预算配额**：每日判断 token 预算按岗位分配（入口 15% / 计划 25% / 闸门 10% / 验收 20% / 优选 20% / 机动 10%）。超配额 → 该岗位当日降级为规则，台账记录。影子双跑的调用计入「机动」配额，采样率 10%。

**批量合并**：同一时刻多个判据请求（如技能优选的 6 个判据）合并为一次前向，按 `native-prompt` 协议拼装，结果按分隔符解析。合并失败自动拆回单条。

### 3.3 取模入口收敛（解决需求 3）

现状是「每个决策点各自取模型」，加槽位不解决问题。方案：

1. **建立单一入口**：新增判断总线模块，作为 L0 的唯一出口。
2. **收敛调用点**：把所有「为判断类任务取模型」的调用点改为 `ask()`。这些调用点分布在：意图/复杂度分类、计划审查、执行前检查、完成度判定、技能与知识优选、成本分层。改造方式是**替换取模语句，不改业务逻辑**。
3. **消除重复实现**：同一判断逻辑存在多份副本的，合并为单一实现，两份调用方共用。
4. **加防护**：加一条静态检查（测试用例形式）——扫描业务模块中直接构造模型客户端做判断的代码，发现即失败。这是防止「判断权再次散落」的机制保障，比一次性清理更重要。

### 3.4 L3 判断资产层：判据技能化 + 三档生效

**判据即技能**：判据不写死在代码里，表达为「判据技能包」，复用现有技能体系（发现、加载、版本、审批、效果评估、回滚）。判据技能包的元数据扩展一段判断声明：

```
judgment:
  post: plan_review          # 所属岗位
  mode: classify             # classify / score / select / gate
  options: [light, medium, heavy]
  thresholds: {heavy_min: 0.62}
  tier: B                    # A 直接生效 / B 影子双跑 / C 红线永不自动
```

代码里只保留「解析器 + 默认判据」，阈值全部外置，可被飞轮改写。

**三档生效（对应需求 5、6）**

| 档 | 语义 | 生效方式 | 适用判据 |
|---|---|---|---|
| **A 直接生效** | 变更只影响「选哪个模型/优先级」，不改变放行与拦截 | 飞轮产出即替换，台账记录 | 成本分层、技能优选、复杂度分档 |
| **B 影子双跑** | 变更影响判断结论但不触碰红线 | 新旧版本并行跑，新版本连续 N 次与人工确认/旧结论一致率 ≥ 阈值才自动升 A；期间旧版本生效 | 计划审查、完成验收 |
| **C 红线永不自动** | 变更可能放宽拦截 | 飞轮只能产出「建议」，必须人工审批 | 执行闸门、安全相关判据 |

**自动回滚与冻结**：判据生效后若效果指标（成功率、返工率、用户否决率）连续劣化超阈值 → 自动回滚上一版本并**冻结该判据**（飞轮不再自动改写，只出建议）。冻结状态在治理面板可见，可人工解冻。

**复用度**：版本链、审批流、效果评估、回滚、台账序列化——这五件套社区版已具备，判断中枢只做「把判据纳入技能体系」的适配，不新建进化引擎。

### 3.5 判据技能包清单（首批 6 个）

| 判据 | 岗位 | 档位 | 说明 |
|---|---|---|---|
| 复杂度分档 | 入口路由 | A | 轻/中/重三档，决定模型档位与上下文预算 |
| 成本分层 | 成本分层 | A | 该轮值得用多贵的模型 |
| 技能优选 | 技能优选 | A | 从可用技能中选出本轮应加载的集合 |
| 知识优选 | 技能优选 | A | 是否引用知识库、引用哪个库 |
| 计划充分性 | 计划审查 | B | 计划是否缺关键步骤、是否可执行 |
| 完成验收 | 完成验收 | B | 声称完成是否真的完成（产物存在、需求覆盖） |

安全闸门沿用现有工具防护机制，判官仅作为「额外建议人工确认」的信号源，归 C 档。

### 3.6 校准闭环

```
判断台账 → 效果归因（该判断后续是否被用户否决/是否触发返工）
        → 阈值/判据建议（飞轮）
        → 影子双跑 → 达标自动生效 / 不达标冻结
        → 台账记录版本与效果曲线
```

效果归因复用现有「技能效果评估」触发点，判断台账作为其新增信号源接入。

### 3.7 判断台账

复用现有经验/台账记录结构，补三字段：`post`（岗位）、`source`（判断来源）、`degraded_reason`。修复台账序列化丢字段问题（状态字段必须持久化，否则影子双跑与回滚判定无依据）。台账存储：社区版沿用现有轻量存储，企业版落 PostgreSQL 审计/台账表（结构化业务表，不进向量库）。

## 4. 六岗位详细设计（对应六个结合点）

每个岗位给出：触发时机、输入、输出、同步性、预算、失败语义。

### P1 入口路由（含成本分层）

- **时机**：用户消息进入，在意图识别与上下文组装阶段。
- **输入**：消息文本、会话历史摘要、附件存在性、当前可用模型清单。
- **输出**：`{复杂度档位, 建议模型档位, 上下文预算档位, 是否需知识库, 是否需技能预热}`。
- **同步性**：**同步，但只走规则**（微秒级）。模型判断以「上一轮预判 + 本轮缓存命中」方式提供，未命中不等待。
- **预算**：规则 5ms；模型补判 300ms（异步，结果作用于本轮后续阶段与下一轮）。
- **失败语义**：完全无判断时 → 沿用现有默认档位，行为与今天一致。
- **价值**：轻任务不必动用重模型，重任务不被轻模型敷衍；成本与质量双向收益。

### P2 计划审查

- **时机**：任务计划生成后、开始执行前。
- **输入**：用户目标、计划步骤列表、可用工具/技能清单。
- **输出**：`{可执行性, 缺失步骤, 风险点, 建议调整}`。
- **同步性**：**异步并行**——计划生成完成后立即启动审查，同时允许执行开始；审查判「不可执行」时，在第一个高风险步骤前打断。
- **预算**：3 秒（与执行并行，不占用户等待）。
- **失败语义**：超时/失败 → 放行并标记「未审查」，台账记录。
- **打断上限**：单次任务审查打断最多 1 次，避免反复拦停。

### P3 执行闸门（安全相关，C 档）

- **时机**：工具调用前，紧接现有工具防护检查之后。
- **输入**：工具名、参数摘要、防护检查结论。
- **输出**：`{是否需要人工确认, 理由}`。
- **同步性**：同步，但**只允许加严**（硬原则 P3）。硬规则判「拦截」时判官无权改；硬规则判「放行」时判官可建议「加确认」。
- **预算**：200ms，超时即按硬规则结论执行。
- **失败语义**：任何失败 → 直接采用硬规则结论，闸门永不因判官不可用而卡住。

### P4 完成验收

- **时机**：智能体声明任务完成之后、回复发出之前（异步）或发出之后（补判）。
- **输入**：用户原始需求、执行摘要、产出物清单（文件路径、链接）。
- **输出**：`{是否真完成, 未覆盖项, 需补做项}`。
- **同步性**：异步。判「未完成」时不撤回已发回复，而是追加一条「补充完成」消息，避免用户等待。
- **预算**：3 秒。
- **失败语义**：失败 → 视为完成，台账记录。
- **价值**：直接针对「说完成了其实没做完」这一最影响信任的问题。

### P5 技能与知识库优选

- **时机**：会话开始预热 + 每轮生成期间并行。
- **输入**：会话主题、技能清单（名称+描述）、知识库清单。
- **输出**：本轮应加载的技能集合、是否引用知识库及目标库。
- **同步性**：会话开始**预热**（首轮即准，解决技能首轮流失）；后续轮走缓存。
- **预算**：预热 2 秒（建立会话时并行，用户无感）；单轮 500ms（以缓存命中为主）。
- **失败语义**：失败 → 沿用现有全量/关键词匹配行为。
- **价值**：技能召回从「关键词命中」升级为「语义优选」，且首轮就生效。

### P6 成本分层

- 并入 P1 输出，不独立调用模型。规则：复杂度档位 × 历史成功率 × 当日预算余量 → 模型档位。
- 预算耗尽时自动降档，在治理面板可见；用户侧仅在高级面板查看。

**岗位间关系**：P1 决定「用多贵的模型」，P2/P3/P4 决定「做不做得下去、算不算做完」，P5 决定「带什么知识去做」，P6 是 P1 的成本约束。六岗位共用同一条总线、同一套台账、同一套预算。

## 5. 关键路径性能设计（解决需求 7）

### 5.1 三时机模型

判断只允许发生在三个时机，绝不在「用户消息 → 首 token」之间同步调用模型：

1. **会话开始预热**：建立会话时并行完成技能/知识优选、历史摘要。
2. **生成期间并行**：计划审查、完成验收、优选补判，全部与生成并行。
3. **生成之后补判**：结果作用于下一轮与台账，不阻塞本轮。

### 5.2 现有同步阻塞治理

现有关键路径上存在一处同步模型调用（意图/复杂度分类相关），实测最坏阻塞约 5 秒，属本方案必须一并治理的存量问题。改造方式：

- 该调用改为「规则先行出结论 → 立即继续 → 模型判断异步补判并写缓存」。
- 下一轮优先读缓存/上轮补判结果，命中即用，未命中用规则结论。
- 净效果：关键路径阻塞归零，判断质量不降（延迟一轮生效）。

### 5.3 性能预算表（硬约束）

| 环节 | 允许占用用户等待 | 说明 |
|---|---|---|
| 入口规则判断 | ≤ 5ms | 纯本地 |
| 入口模型补判 | 0（异步） | 缓存供后续轮 |
| 计划审查 | 0（并行） | 打断在步骤间隙 |
| 执行闸门 | ≤ 200ms | 超时即放行 |
| 完成验收 | 0（异步） | 追加补充消息 |
| 技能优选 | 0（预热/缓存） | 会话开始并行 |
| 判断总开销 | 每轮 ≤ 1200ms 且全部在关键路径外 | 由预算配额保证 |

### 5.4 吞吐与成本

- 缓存命中目标 ≥ 40%（技能优选、复杂度分档重复度高）。
- 批量合并把多判据合并为一次前向，优选岗位调用次数下降约 5/6。
- 影子双跑采样 10%，总判断成本增幅控制在 +10% 内。
- 每日 token 预算封顶，超配额自动降级，不会无限烧钱。
- 本地量化判别模型（约 3GB 显存）在现有 4 卡环境下可与生成模型共存，无需让卡。

## 6. 交互与分层暴露设计（解决需求 8）

遵循「默认简单，按需复杂；AI 做决策，用户做选择；功能不消失，只是隐藏」。

### 6.1 第一层 · 无感层（80% 用户看到的）

- 判断中枢**完全不出现在聊天界面**。用户看到的聊天界面与今天一致。
- 唯一可见元素：判断能力降级时，在输入区旁出现一枚极小的状态标识（如「规则模式」灰点），hover 一句话解释「智能判断暂不可用，已按规则运行，不影响使用」。不弹窗、不打断、不要求用户处理。
- 判官建议人工确认时（P3），沿用现有工具确认交互，文案给出**理由**（「该命令会删除工作区外文件，建议确认」），并附「本次继续 / 查看判断详情」。

### 6.2 第二层 · 引导层（判断介入时的对话式交互）

- 计划审查判「不可执行」→ 不中止任务，而是在对话里给一条建议卡片：「我注意到计划里缺少 X，建议先做 X。要我调整计划吗？【调整 / 按原计划继续】」。
- 完成验收判「未完成」→ 追加一条「补充」消息，把未覆盖项做完，标题为「补充：还差 2 项」。
- 原则：判断永远以「给用户一个选择」的形式出现，绝不以「阻止用户」的形式出现（红线安全除外）。

### 6.3 第三层 · 治理面板（管理端，高级面板）

新增一个「智能判断」面板，五块内容：

| 区块 | 内容 |
|---|---|
| 能力状态 | 判断槽当前模型、探测结果、延迟分位、熔断状态 |
| 判断概览 | 近 7 天判断次数、覆盖率、降级率、缓存命中率、预算用量 |
| 判据清单 | 每个判据的档位（A/B/C）、当前版本、生效方式、效果曲线 |
| 影子双跑 | 新旧版本一致率、分歧样本、达标进度 |
| 台账检索 | 按会话/岗位/来源筛选判断记录，可导出 |

面板入口放在管理端，不进普通用户菜单。所有参数（预算、采样率、熔断阈值）在面板内以**预设档位**呈现（保守/均衡/积极三档），不暴露裸参数——满足「想找到都能找到」同时不制造配置负担。

### 6.4 配置面

- 判断模型的选择 = 在现有模型配置里把某个模型标记为「判断」用途，与现有五类用途标记同构，无新界面范式。
- 不新增环境变量，不新增配置文件项暴露给部署者之外的用户。

## 7. 安全与红线（解决需求 11）

1. **红线判定与判官解耦**：破坏性命令、越权路径、外部副作用的拦截由既有硬规则（工具防护）决定，判官无投票权。
2. **判官只加严不放宽**：判官输出只能提升确认等级，不能降低。任何「判官建议放行」不得覆盖「规则判定拦截」。
3. **判官不可用时安全行为不变**：熔断/降级路径下，安全闸门完全退化为纯规则，行为与今天一致。
4. **C 档判据永不自动生效**：飞轮对安全相关判据只能产出建议，必须人工审批，审批走现有技能审批流。
5. **台账不记录敏感正文**：判断台账只存输入指纹（哈希）与结论，不存用户消息原文与文件内容，避免台账成为数据泄露面。
6. **数据不出域**：默认优先本地判别模型；启用外部决策 API 时，判断输入需经脱敏（去手机号/身份证/密钥样式），并在治理面板显示「判断输入已外发」开关与审计记录。
7. **预算与频率限制**：判断调用受每日预算与熔断双重限制，防止判断环节被滥用为放大攻击面。

## 8. 数据模型与接口契约

### 8.1 新增/扩展数据结构

| 名称 | 位置 | 字段要点 |
|---|---|---|
| 判断槽位 | 模型配置体系 | 用途标记 `judgment`，指向一个已配置模型 |
| 能力画像 | 运行时（内存，可缓存） | available / protocol / latency_p95 / supports_json_schema / max_batch_questions / cost_per_1k |
| 判断请求 | 总线入参 | post / criteria_id / mode / input / options / deadline_ms / session_ref |
| 判断结果 | 总线出参 | decision / confidence / source / degraded / criteria_version / latency_ms / cost / judgment_id |
| 判断台账 | 轻量存储（社区）/ 审计台账表（企业 PG） | 复用现有经验记录 + post + source + degraded_reason；修复状态字段序列化丢失 |
| 判据技能包 | 技能体系 | 元数据新增 judgment 段（post/mode/options/thresholds/tier） |
| 影子运行记录 | 台账派生 | criteria_id / 新旧版本 / 逐次结论 / 一致标记 |

### 8.2 接口（治理面板用，全部挂在既有管理端路由下）

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | 判断能力状态 | 当前判断槽、探测结果、熔断状态 |
| GET | 判断概览 | 近 N 天统计（覆盖率/降级率/命中率/预算） |
| GET | 判据清单 | 判据列表 + 档位 + 版本 + 效果 |
| POST | 判据档位调整 | 人工把 B 升 A、C 审批生效、解冻冻结判据 |
| GET | 影子双跑详情 | 一致率与分歧样本 |
| GET | 台账检索 | 按会话/岗位/来源分页查询 |

企业版扩展：台账与影子记录落 PostgreSQL；判据技能包可被企业知识库检索增强（复用现有知识库能力，不新建存储）。社区版接口保持不动，企业版只新增扩展路径，不复制社区实现。

### 8.3 兼容与迁移

- 判断中枢关闭（判断槽未配置）时，系统行为与当前版本**逐字节等价**——所有岗位退化为现有规则路径。这是灰度与回滚的基础。
- 提供单一开关（内部配置，非环境变量）：`judgment_hub.enabled`，默认关闭，逐岗位开启。

## 10. 验收标准（可测）

**功能**

1. 判断槽未配置时，全量回归测试通过，行为与基线版本一致。
2. 判断槽配置后，六岗位台账均出现记录，`source` 分布可见。
3. 台账状态字段可完整读出（序列化往返无损）。
4. 判据版本变更后，影子双跑记录生成，达标自动生效、不达标冻结，两条路径均可复现。
5. 冻结判据不再被飞轮自动改写。
6. 判官不可用时，安全闸门行为与基线一致（用例：破坏性命令仍被拦）。
7. 判官建议不得降低拦截等级（用例：规则拦截 + 判官放行 → 结果拦截）。

**性能**

8. 首 token 延迟：开启中枢后不高于基线（目标下降 ≥ 20%）。
9. 关键路径无同步模型调用（静态检查 + 运行时埋点双重验证）。
10. 判断缓存命中率 ≥ 40%（技能优选岗位）。
11. 每日判断 token 用量不超配额，超配额自动降级并留痕。

**治理**

12. 治理面板五块内容均有真实数据。
13. 降级状态在界面可见且不打断聊天。
14. 台账不含用户消息原文（抽样检查）。

## 13. 关键设计决定一览（已锁定，无待决项）

| 决定 | 内容 |
|---|---|
| 判断模型形态 | 判别式小模型优先（本地量化约 3GB 显存），外部决策 API 备选，生成模型判别模式过渡 |
| 接线方式 | 判断总线为唯一入口，槽位只登记不绑定，代码不决定用哪个模型 |
| 兜底 | 四级回落链，绝不抓第一个可用模型 |
| 熔断 | 进程级 3 次失败 / 600 秒冷却 / 2 秒探针，参数内置不暴露 |
| 生效 | 三档（A 直接 / B 影子双跑 / C 红线永不自动）+ 连续劣化自动回滚冻结 |
| 性能 | 关键路径零同步模型调用；三时机模型；每轮判断开销 ≤ 1200ms 全在关键路径外 |
| 安全 | 判官只加严不放宽；红线由硬规则独占；台账只存指纹 |
| 交互 | 三层暴露；判断以「给选择」而非「阻止」出现；不新增用户配置项 |
| 复用 | 台账/版本/审批/效果/回滚五件套全部复用既有机制，不新建引擎 |
| 回退 | 开关关闭时与基线行为等价，支持逐岗位灰度 |
