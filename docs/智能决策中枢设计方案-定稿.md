## 1. 设计目标与原则

**目标**：让系统从"只会执行"升级为"会判断"——判断任务难度、判断该用哪个模型、判断计划是否可行、判断结果是否真的完成、判断该调哪个技能/知识、判断该花多少钱。

**五条硬原则**（任何实现不得违反）：

1. **判断与生成分离**——判断是独立能力层，不寄生在对话模型里，不随对话模型配置漂移。
2. **判断永不阻塞生成**——用户可感知的关键路径上，绝不同步等待模型判断。
3. **判断权是资产不是代码**——判据（阈值、选项、模式）外置、可版本化、可回滚、可审计。
4. **缺位即降级，降级即可见**——没有判断模型时系统必须正常工作，且用户/管理员知道它在降级运行。
5. **默认简单，按需复杂**——普通用户看不到任何"决策模型"概念；所有旋钮在管理端。

## 2. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│ L4 治理与可观测   判断台账 · 效果闭环 · 降级可见 · 预算看板      │
├─────────────────────────────────────────────────────────────┤
│ L3 判断资产层     判据技能包（版本/审批/影子双跑/三档生效/回滚）  │
├─────────────────────────────────────────────────────────────┤
│ L2 判断岗位层     P1入口路由 P2计划审查 P3执行闸门 P4完成验收     │
│                  P5技能与知识优选 P6成本分层                    │
├─────────────────────────────────────────────────────────────┤
│ L1 判断总线       ask() 唯一入口 · 四级回落 · 熔断 · 缓存 · 预算 │
├─────────────────────────────────────────────────────────────┤
│ L0 判断能力层     判断槽位 · 能力探测 · 判别式模型/生成模型/API   │
└─────────────────────────────────────────────────────────────┘
```

**一句话读懂**：L0 提供"能判断的模型"，L1 提供"唯一且安全的取用方式"，L2 是"六个具体干活的岗位"，L3 让"判断标准可以像软件一样迭代"，L4 让"这一切可度量、可信任"。

**核心概念（术语定名，后续代码/文档统一用这套）**：

| 术语 | 含义 |
|---|---|
| 判断槽位 judgment slot | 模型配置体系里新增的第 6 类槽位，专用于判断，与对话/向量/图像/音频/语音并列 |
| 判断总线 judgment bus | 全系统唯一的判断取模入口，所有岗位必须经它取模型 |
| 判断请求 JudgmentRequest | 一次判断的输入契约（岗位、判据id、输入指纹、超时、预算） |
| 判断结论 JudgmentOutcome | 一次判断的输出契约（结论、置信、依据、来源档位、耗时、是否降级） |
| 判据 criteria | 一个可版本化的判断标准单元，以技能包形式存在 |
| 生效档位 tier | 判据的自动化等级：A 直接生效 / B 影子双跑 / C 永不自动 |
| 影子双跑 shadow run | 新旧判据同时跑、只记录不生效，达标后自动升级 |
| 降级档位 fallback level | 结论来自哪一级：L1判断槽 / L2对话槽 / L3规则 / L4保守默认 |

## 3. 核心组件设计

### 3.1 L0 判断能力层

**3.1.1 判断槽位**

在现有模型配置体系里新增槽位类型 `judgment`，与既有五类槽位同级。要点：

- 槽位记录必须携带**用途标签**（judgment / chat / embedding / image / tts / stt），取模时按标签匹配，**彻底废除"取第一个可用模型"这类兜底**。
- 判断槽位允许为空。为空不是错误，是"降级运行"状态，由总线处理（见 3.2.3）。
- 判断槽位支持多模型登记，带优先级与能力标签（是否支持批量、是否支持严格 JSON 输出、平均延迟）。

**3.1.2 能力探测（capability probe）**

系统启动时 + 每 30 分钟，对判断槽位里的每个模型做一次轻量探测：

- 发一条固定探针请求，测连通性与延迟；
- 探测结果形成**能力描述符**：`{可用, 平均延迟ms, 协议, 支持批量, 支持严格结构化输出, 上下文上限}`；
- 探测失败 → 该模型标记不可用，进入熔断观察；
- 探测本身**不占用**判断预算，不进台账。

**3.1.3 规格定义（决策模型该是什么样的）**

判断任务与对话任务性质相反：要**快、稳、听话**，不要聪明。

| 维度 | 要求 | 说明 |
|---|---|---|
| 参数量 | 0.3B ~ 4B | 判别式优先；生成式需能强制结构化输出 |
| 响应延迟 | P50 ≤ 800ms，P95 ≤ 2s | 超过则自动降级为规则 |
| 输出纪律 | 严格 JSON，枚举取值，禁止自由文本 | 解析失败即判为失败 |
| 上下文 | ≥ 4K 足够 | 判断输入是摘要不是全文 |
| 部署形态 | 本机量化 / 内网自托管 / 外部 API | 三形态并存，按优先级取用 |
| 温度 | 0 | 判断要可复现 |

**3.1.4 四级能力路线（本机现实）**

按"效果/成本/可控性"排序，系统按优先级自动取用：

1. **外部决策 API**（百炼决策系列等）——零运维、质量最高、有网络依赖与配额成本。
2. **内网自托管**（本机 4×2080Ti 跑 4B~8B 判别式，OpenAI 兼容端点）——延迟可控、数据不出内网。
3. **本机量化**（0.8B 级 4bit 量化，约 2.7GB 显存，llama.cpp / vLLM 起服务）——完全离线，质量中等，作为默认生产形态。
4. **生成模型判别模式**（现有对话模型 + 强制 JSON 输出 + 极短提示）——过渡形态，质量可用但慢且贵，仅用于影子双跑与冷启动。
5. **规则引擎**——永久兜底，永不删除。

> 落地建议：**一期用第 4 级跑通链路并积累台账，三期把第 3 级本机量化模型接上，第 1 级作为可选增强**。这样一期不依赖任何新硬件与新采购。

### 3.2 L1 判断总线（本方案的中枢）

**3.2.1 唯一入口**

```
bus.ask(JudgmentRequest) -> JudgmentOutcome
```

全系统所有判断**只能**经这一个函数。任何岗位不得自行取模型、自行拼提示词。这是"五个槽位写死"问题的根治手段：岗位只声明"我要判什么、用哪条判据"，模型由总线决定。

**3.2.2 请求/结论契约**

```
JudgmentRequest:
  post          岗位标识（P1..P6）
  criteria_id   判据id（决定提示词、选项、阈值、生效档位）
  payload       判断输入（结构化，摘要级，≤1K token）
  mode          sync | async
  budget_ms     本次允许的最大耗时
  allow_chat    是否允许回落到对话模型（默认否，仅低敏感岗位开）

JudgmentOutcome:
  verdict       结论（判据定义的枚举值）
  confidence    置信 0~1
  reason        一句话依据（供台账与用户引导话术）
  source        L1判断槽 | L2对话槽 | L3规则 | L4保守默认
  latency_ms    实测耗时
  degraded      是否降级（source != L1 即为真）
  criteria_ver  生效判据版本（供影子双跑与回滚定位）
```

**3.2.3 四级回落链（缺位保障）**

```
判断槽可用？ ──是──> 用判断槽（source=L1）
     │否
对话槽可用 且 allow_chat 且 判据档位≠C？ ──是──> 用对话模型判别模式（source=L2）
     │否
规则引擎覆盖该判据？ ──是──> 规则结论（source=L3）
     │否
返回该判据的保守默认值（source=L4，degraded=true）
```

**保守默认值的设计要求**：每条判据必须显式声明"判不了时怎么办"，且默认值一律取**对用户最不打扰**的一侧——

- 计划审查判不了 → 放行（不阻断用户）
- 完成验收判不了 → 放行（不否定智能体的完成声明）
- 执行闸门判不了 → 沿用现有安全规则结论（安全侧不放松）
- 入口路由判不了 → 沿用现有规则档位

**3.2.4 熔断器**

- 粒度：进程级，按模型（不是按岗位）。
- 触发：连续 3 次失败（超时/解析失败/HTTP 错误）。
- 冷却：600 秒内直接走回落链，不再尝试该模型。
- 探针：冷却到期后放 1 次 2 秒超时的探针请求，成功即恢复。
- **不暴露为用户配置**，避免用户调参数把系统调挂。
- 熔断状态变化写入运行日志并计入降级计数。

**3.2.5 判断缓存**

- 键：`(criteria_id, 输入指纹, 判据版本)`
- 判据版本变更 → 该判据缓存整体失效（保证新判据立即生效）。
- 容量上限 + 条目 TTL（默认 300 秒），**必须有容量上限**，防止无界增长。
- 命中直接返回，`latency_ms≈0`，台账记 `cache_hit`。
- 缓存只存 L1/L2 结论；L3/L4 不缓存（规则本就廉价）。

**3.2.6 批量合并**

外部决策 API 支持"一次前向、多问题、多套选项"。总线提供 `ask_batch([req...])`，把同一时刻的多个判断合成一次调用。P1 入口路由与 P6 成本分层天然合并；技能优选的多个候选合并为一次多选判断。

### 3.3 L2 判断岗位层（六岗位规格）

每个岗位按同一模板定义：**时机 / 输入 / 结论 / 同步性 / 预算 / 失败语义 / 生效档位**。

| 岗位 | 时机 | 输入 | 结论（枚举） | 同步性 | 预算 | 判不了时 |
|---|---|---|---|---|---|---|
| **P1 入口路由** | 用户消息到达，生成之前 | 消息文本 + 会话上下文摘要 + 可用技能清单摘要 | 复杂度档位（极简/常规/复杂/超长）+ 建议模型档位 + 建议技能 | **同步仅走规则；模型判断异步补判** | 规则 ≤5ms；模型 300ms | 用规则档位 |
| **P2 计划审查** | 计划生成后、执行前 | 计划步骤列表 + 资源约束摘要 | 可行 / 需调整 / 明显不可行 + 理由 | 异步（与首步执行并行） | 3s | 放行并标记 |
| **P3 执行闸门** | 工具调用前 | 工具名 + 参数摘要 + 影响面 | 放行 / 需人工确认 / 拦截 | **红线同步（纯规则）；判官仅异步标注** | 规则 ≤2ms | 沿用现有安全规则 |
| **P4 完成验收** | 智能体声明完成之后 | 用户原始诉求 + 产出摘要 + 验收判据 | 已满足 / 部分满足 / 未满足 + 缺什么 | 异步 | 3s | 放行 |
| **P5 技能与知识优选** | 会话开始预热 + 每轮缓存命中 | 意图 + 技能/知识条目摘要 | 最相关的 ≤3 个技能 + ≤3 个知识条目 | 预热异步，命中同步 | 预热 2s/轮 | 用全量注入 |
| **P6 成本分层** | 并入 P1 | 同 P1 | 模型档位 + 是否跳过深度思考 + 上下文预算建议 | 随 P1 | 0（合并） | 用默认档位 |

**关键设计说明（这三条是方案的核心，务必实现）**：

1. **P1 的"同步规则 + 异步补判"**：用户消息进来，规则引擎立刻给出档位（微秒级），生成立即开始；同时总线异步发起模型判断，结论**用于下一轮**并写入台账。这样模型判断的收益照拿，用户零等待。
2. **P3 的红线永不下放**：破坏性命令、越权路径、外发拦截等安全判定**只由现有安全规则引擎决定**，判官只做"额外建议人工确认"的加法，绝不做"放行"的减法。判官无权放松安全。
3. **P4 是新增能力**：现有系统缺"完成度验收"，这是用户可感知价值最直接的一环——智能体说"做完了"，判官核对"用户到底要什么"，不满足就自动继续，而不是等用户发现没做完。

### 3.4 判据资产化（L3）

**3.4.1 判据即技能**

每条判据是一个技能包，frontmatter 扩展判断段：

```yaml
judgment:
  post: P1                    # 所属岗位
  mode: single_choice         # single_choice | multi_choice | score
  options: [极简, 常规, 复杂, 超长]
  thresholds: {token_超长: 12000, 技能命中数: 3}
  tier: B                     # A直接生效 / B影子双跑 / C永不自动
  conservative_default: 常规   # 判不了时的保守值
  allow_chat_fallback: true
```

**代码只负责**：取判据 → 拼提示 → 调总线 → 解析 → 执行结论。**代码不再包含任何阈值、选项、模式判断**。这是"判断权上收"的落地形态。

**3.4.2 三档生效（回答"飞轮产出能否自动生效"）**

| 档位 | 适用判据 | 生效方式 | 理由 |
|---|---|---|---|
| **A 直接生效** | 纯参数类：阈值、预算、采样率、选项增删 | 飞轮产出 →
