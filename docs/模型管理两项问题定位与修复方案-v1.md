## 0. 用户口径（原话）

1. 「增加了 qwen-flash 提供商，手动只是增加了 2 个模型，但是却把所有模型给我拉回来了。这不必要，模型太多选择性困难，只是需要我手动增加的即可。」

## 1. 现象复核（全部实测，非推测）

### 1.1 qwen-flash 实际存量 = 21 个模型（用户只手动加了 2 个）

```
/apps/ai/coapis-dev/system/.secret/providers/custom/qwen-flash.json   mtime 2026-11-02 09:47
model count: 21   全部 source="added"   max_sequence_length 全为 None
  qwen3.7-max / qwen3.7-plus / qwen3.6-flash / glm-5.2 / deepseek-v4-pro /
  wan2.7-image / wan2.7-image-pro / qwen-audio-3.0-tts-plus /
  deepseek-v4-flash-0731 / qwen3.8-max / qwen-audio-3.0-realtime-plus /
  deepseek-v4-pro-0813 / qwen3.8-flash / deepseek-v4.1-flash / glm-5.3 /
  auto / decision-model-preview / wan3.0-video / deepseek-v4.1-flash-1017 /
  qwen-image-3.0-pro / qwen-audio-3.0-asr-flash
```

容器内实测该网关的 `/v1/models`：

```
stored models: 21
gateway models: 21        # 与落盘清单逐一对齐，顺序一致
would-be-new: 0
```

→ **落盘 21 个 = 网关全量 21 个，逐一相等**（`would-be-new: 0`）。用户手动添加的那 2 个也在网关目录里，而探针写入的模型被标成 `source="added"`（`provider_manager.py:992`），**所以文件里 21 个模型全部是 `source="added"`——系统层面已无法区分"用户手加的 2 个"与"探针灌进来的 19 个"**。这正是 A2（来源标记语义修正）必须做的理由：不修标记，任何"只保留手动"的策略都没有判据。

### 1.2 探针落盘时间与文件 mtime **逐秒吻合**（三个 provider 各自铁证）

`coapis.log` 共 12 次探针，其中三次与 provider 文件 mtime 完全对到同一秒：

| 探针日志时间（coapis.log） | provider | 文件 mtime |
|---|---|---|
| 2026-10-19 18:05:26 | local_vllm | `custom/local_vllm.json` = 2026-10-19 **18:05:26**.402943032 |
| 2026-10-23 15:30:03 | coapis | `custom/coapis.json` = 2026-10-23 **15:30:03**.376976003 |
| 2026-11-02 09:47:49 | **qwen-flash** | `custom/qwen-flash.json` = 2026-11-02 **09:47:49**.752896752 |

qwen-flash 被探针命中 **7 次**（10-20 15:25、10-21 09:49、10-22 15:19、10-22 16:32、10-28 10:11、10-28 11:19、11-02 09:47），每次都执行"全量发现 + 落盘"：

```
2026-11-02 09:47:49 | INFO | coapis/providers/provider_manager.py:1075 |
  Context-window probe for provider 'qwen-flash' reported no window;
  the context budget keeps the configured max_input_length
```

正因如此，用户删掉的模型会在下一次会话被重新灌回——"拉回来"。

| `ConfiguredModelsSection.tsx:213` | 「设为默认」按钮 `onSetDefault(r.model.model_type, …)` —— **只能按模型自身类型写槽**，聊天模型永远无法成为"决策模型" |

## 2. 根因

### 根因 A（问题 1 主犯）：上下文窗口探针会把网关全量模型**无条件落盘**

调用链（每一环都按当前 HEAD 源码逐行核对）：

```
会话/模型解析 → agents/context/window_source.py:244-257
  if result.source != "model_self_report" and provider_id:
      ProviderManager.get_instance().request_window_probe(provider_id)
→ providers/provider_manager.py:1022 request_window_probe   （30 分钟节流：_WINDOW_PROBE_MIN_INTERVAL = 1800.0，:1020）
→ :1056 _window_probe_task
→ :1064 await self.fetch_provider_models(provider_id, save=True)      ← 元凶
→ :958-992 合并策略 = 「已有清单 ∪ 网关全量」，新模型 m.source = "added"（:992）
→ :1005 self._save_provider(provider)  整体落盘
```

关键性质（全部实测/逐行核对）：

- **探针没有任何护栏。** `_window_probe_task` 现在只写了一行 `fetch_provider_models(provider_id, save=True)`，**不检查 `support_model_discovery`、不检查 `is_local`**（源码 1056-1071 全文即"try → fetch → 打日志"）。qwen-flash 文件里 `support_model_discovery=False` 也照灌——这条路径对**任何** provider 都成立。
- **触发条件是"模型不自报上下文窗口"**。qwen-flash 的 21 个模型 `max_sequence_length` 全为 `None` → 只要用这个 provider 聊一句，探针必然触发（30 分钟一次）。
- **`save=True` 无边界**：网关返回多少就落多少（网关实测 21 个 = 落盘 21 个）。
- **探针写入的新模型被标成 `source="added"`**（`provider_manager.py:992`），与用户手动添加**完全不可区分** → 系统没有任何依据判断"哪些是用户要的"。
- **删了会回来**：用户删掉多余模型后，下一轮会话探针再次把网关全量灌回 → 正是"把模型给我**拉回来**了"（qwen-flash 被探针命中 7 次）。
- UI 里唯一的显式入口同样激进：`RemoteModelManageModal.tsx:673 api.discoverModels(id, undefined, true)`，后端 `DiscoverModelsRequest.save` 默认 `True`（`providers.py:456`），`/models/{id}/discover` 一次全量入库。
- 探针的**收益**要保留：`local_vllm` 探针成功回 `{'Q3': 102400}`（10-19 18:05:26 日志）——这正是上下文预算需要真实窗口的场景。所以治本方向是"只补窗口、不扩清单"，**不是关掉探针**。

### 根因 B（问题 1 从犯）：用户没有任何办法告诉系统"窗口就这么多"

- `ModelConfigRequest`（`providers.py:214`）只有 `generate_kwargs`；`Provider.update_model_config`（`provider.py:389`）只写 `generate_kwargs`。
- 前端模型管理里**没有上下文窗口输入框**（全量 grep `max_sequence_length` 在 Models 页面 0 命中）。
- 后果：网关不自报窗口 + 用户填不了窗口 ⇒ 探针**永远触发**，问题不可自愈。

### 根因 C（问题 2）：判官模型是"配置文件里的裸字符串"，不是"模型资产"

判官槽位（`decision/config.py:65-66 judge_provider_id/judge_model`）与模型管理是**两套平行世界**：

- 模型管理的世界：5 类 × `DefaultModelsConfig` 槽位，有 tabs、默认栏、"设为默认"按钮。
- 判官的世界：`decision_hub.json` 两个字符串，靠 resolver 解析（`resolver.py:209`），**零 UI**。
- 两边互不相认：模型管理里怎么点都写不到 `judge_*`；`/decisions/config` 里没有模型选择器。

### 根因 D（问题 2 的设计约束，必须写进方案）

判官有硬校验 `resolver.assert_chat_capable()`（`resolver.py:73-110`）：**候选模型 `model_type` 必须是 `chat`**，否则直接挡掉（这是"嵌入模型当判官"的根治点）。

→ 所以**绝不能把某个模型的"主类型"改成 decision**：那样判官会被自己的校验挡死，判官永远不上岗。
→ 正确形态：`决策模型` 是**第 6 个默认槽位**（槽位是"用途"，不是"模型主类型"）。这是本方案的关键取舍，也是它与"直接加第 6 个枚举值"的区别。

## 3. 修复方案

### A 批 —— 只保留手动添加的模型（问题 1）

| 编号 | 改动 | 文件:行 | 说明 |
|---|---|---|---|
| **A1** | 探针**只补窗口，不扩清单**（治本核心） | `providers/provider_manager.py:926` `fetch_provider_models` 增参 `persist_new_models: bool = True`；`:1064` 探针路径传 `False` | `False` 时：只对**已存在**模型写 `max_sequence_length`（窗口收益 100% 保留），**不新增任何模型**。既有测试 `test_window_source_b2.py::test_discovery_fills_a_missing_window_and_never_clobbers_a_real_one` 继续绿 |
| **A2** | 来源标记语义修正 | `provider_manager.py:992`、`:1230 add_model_to_provider` | 网关/发现写入 → `source="discovered"`；用户手动添加 → `source="added"`。给"只保留手动"提供可判定依据（列表徽标 + 一键清理都靠它） |
| **A3** | provider 级 `manual_models_only`（默认 True，仅自定义 provider） | `providers/provider.py` `ProviderInfo` 增字段；`fetch_provider_models` 入口判断 | True 时任何自动路径（探针/发现/注册插件）都不得新增模型；UI 提供开关"允许自动同步网关模型列表"，勾上才恢复现在的全量行为 |
| **A4** | 发现改成**预览式** | `app/routers/providers.py:456` `DiscoverModelsRequest.save` 默认改 `False`；前端 `RemoteModelManageModal.tsx:673` 传 `false` + 候选清单勾选后逐个 `addModel` | 点"自动获取模型"只**展示**候选，用户勾选才入库。OpenRouter 分支已是此模式（`handleAddFilteredModel` 逐个加），对齐即可 |
| **A5** | 模型级**上下文窗口**可填 | `providers/provider.py:389 update_model_config` 支持 `max_sequence_length`；`providers.py:214 ModelConfigRequest` 加字段；前端模型行加输入框 | 用户填了窗口 → `source == "model_self_report"` 分支成立 → 探针**不再触发**，与 A1 形成双保险 |
| **A6** | 存量清理 | 一次性脚本（`scripts/` 下，不动代码逻辑） | 因 `source` 已被探针污染（21 个全是 `added`），脚本**必须显式指定保留清单**（`--keep qwen3.8-flash,xxx`），绝不猜；`--dry-run` 先打印将删除的 19 个，确认后再执行。顺带清 `auto` 这类非模型 ID 脏项 |
| **A7** | 防"默认模型被清成空" | 复用 `_clear_stale_default_models`（`:1329`） | 清理脚本删除的模型若正被槽位引用，同步清槽并提示，不制造悬空默认 |

**A 批影响面（实测调用点，共 3 处 + 测试）**：`fetch_provider_models` 定义在 `provider_manager.py:926`；调用方只有 ① `provider_manager.py:1059` 探针（改传 `persist_new_models=False`）、② `app/routers/providers.py:554` 发现接口（传 `save` 原样，A4 改默认值）、③ `server/configure_llm.py:24` CLI 脚本（保持全量），另有 `server/tests/unit/test_window_source_b2.py:271` 断言"补齐已有模型的窗口、绝不覆盖用户设置"——A1 必须让这条测试继续绿。OpenRouter 走的是独立接口（`providers.py:1140 discover_openrouter_extended` / `1101 series`），不受影响。内置 provider（OpenAI/Ollama/Gemini/Anthropic）的目录能力依赖发现接口，故 A3 的 `manual_models_only` 默认值**只对 `is_custom=True` 生效**，内置 provider 行为不变。

### B 批 —— 决策模型成为第 6 个可管理/可默认的分类（问题 2）

## 5. 验收标准（逐条可测）

1. qwen-flash 清理后剩 2 个模型；用它连续发起 10 轮会话（含探针节流窗口外的第 31 分钟），`providers/custom/qwen-flash.json` 的 `models` 长度**恒为 2**，且这 2 个模型的 `max_sequence_length` 被探针成功补齐（`>0`）。
2. `coapis.log` 中 `Context-window probe ... succeeded` 之后**不再出现**模型数量增长；`grep -c` 前后对比。
3. 「自动获取模型」按钮点击后**不写盘**：返回候选清单，未勾选前 `providers/*.json` mtime 不变。
4. 模型管理页默认模型栏出现 6 个 chip，第 6 个为「决策模型」；设置后 `default_models.json` 出现 `decision` 节点，重启后仍在。
5. 决策模型槽选 embedding/rerank 模型 → API 返回 400，前端提示"判官必须是对话模型"。
6. 设置决策模型后发一轮会话，判断中枢浮窗显示"判官模型：provider/model（来源：决策模型槽）"，台账 `decision_events` 出现 `model` = 该模型、`真判` 记录。
7. 旧 `default_models.json`（无 `decision` 字段）在升级后启动**不再**报 "Failed to load default models"。
8. 全量测试全绿；dev 部署 1.2.x 后浏览器实测三条链路（列表稳定 / 决策槽设置 / 判官真判）截图留证。

## 6.5 落地时的三处雷点（已核对，写代码时照此走）

1. **`/models/default-models` 的真正处理器只有一个**：providers 路由的 prefix 就是 `/models`（`app/routers/providers.py:39`），所以前端 `api.get/put("/models/default-models")` 命中 `providers.py:1273/1334`。`app/routers/models.py:223-252` 里的 `POST /default`、`GET/PUT /default-models` 是**桩函数且该 router 从未注册**（`app/routers/__init__.py` 只 `include_router` 了 providers/local_models 等，无 models_router）→ 属死代码，B5 只改 providers.py 一处，不要顺手"修"models.py 造成两处语义。
2. **前端没有 api 层封装**：`index.tsx:39/67` 直接裸调 `api.get/put`，类型是页面内临时声明的 `Record<string, DefaultModelSlot>`（`index.tsx:25`）。B5 收口时把类型与调用一起提到 `client/src/api/modules/provider.ts`，避免第 6 槽在前端各处各自断言。
3. **默认槽是"全局"，判官有"智能体级覆盖"**：`user_model_prefs.py:307`（用户偏好缺失时取 `global_slot = ProviderManager.get_active_model()`）已经证明——作用域只有"全局槽 → 用户/智能体覆盖"两级。所以 B4 的优先级（智能体覆盖 → hub 旧键 → 全局决策槽 → 无判官）与现有 per-user/per-agent 机制同向，不新增第三套作用域。
