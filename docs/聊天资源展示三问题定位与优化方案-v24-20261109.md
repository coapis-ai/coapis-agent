# 聊天「资源」展示三问题定位与优化方案 v24（2026-11-09）

> 状态：**方案，未改一行代码**。实测环境 = dev 社区版 172.16.6.241:4300 / v1.2.18（admin 登录 + 浏览器实测 + API 实测）。
> 提出人：小蜜蜂。三条问题 + 一条总纲（统一组件、站在用户体验角度）。

---

## 0. 小蜜蜂原话（拆成 3 + 1）

1. 左栏会话列表的当前会话，把下拉显示宽度放大些，可以和当前会话的卡片对齐；同时是不是应该和聊天界面中类似 —— **为什么要分成两个下拉？**
2. 聊天界面「会话资源」有「引用、产出、展开（有下拉）、查看全部、判断」，**有点乱**。下拉是否直接放在「引用、产出」上面？各自点击展示各自的；**「判断」是做什么用的？我觉得判断应该只是类似审计日志，不应该显示给用户。**
3. 资源列表里有**已经删除的文件**，既然已删除就不要保留，避免留错误给用户。
4. 总纲：**不需要那么复杂，是否可以统一成一个组件？** 或者这个组件只在左栏会话中显示，聊天界面只显示当前步骤的引用和生成 —— 现在不知道是当前步骤的。

## 1. 实测证据（dev v1.2.18，浏览器 DOM 实测 + API 实测）

### 1.1 左栏宽度：资源行只有会话卡片的 70%（问题 1 实锤）

| 元素 | 宽 | left | right | 相对卡片的偏移 |
| --- | --- | --- | --- | --- |
| 左栏容器 `.sidebar` | 300px | 265 | 565 | — |
| **会话卡片**（`.lineWrap > *`） | **283px** | 273 | 556 | 基准 |
| **资源行**（左栏面板里的 `li`） | **198px** | 295 | 493 | **左缩 22px / 右短 63px** |
| 资源行名称可用宽 | 55 ~ 182px | 303 | — | 名称被 ellipsis 吃掉 |

缩进的来源链（每一层都在吃宽度，没有一处是设计意图，都是历次批次叠加）：

```
ChatSessionDropdown .list      padding: 0 8px            （会话卡片同一层）
ChatSessionItem    .item       padding: 10px 12px 10px 8px   ← 卡片文字基线：左8 右12
ChatSessionResources .panel    margin: 0 8px 6px 0        ← 右 -8
                               padding: 0 10px 6px 10px   ← 左 +10 右 -10
                         .body  margin: 2px 0 0 2px
                               padding: 0 0 0 2px         ← 左 +4
                         .list  padding: 2px 4px 2px 17px ← 左 +17
──────────────────────────────────────────────────────────
左内缩 10+4+17 = 31px（卡片基线 8px）→ 视觉深 23px
右内缩  8+10   = 18px（卡片基线 12px）→ 视觉短  6px
实测行宽 198px = 卡片 283px 的 70%
```

### 1.2 聊天区资源条头部：一行挤了 5 个控件（问题 2 实锤）

浏览器实测头部文本，一字不差：

```
会话资源 | 引用 3 | 产出 2 | 展开 | 查看全部 | 判断
```

DOM 实测「看起来能点」的东西 = `引用 3`、`产出 2`、`展开`、`查看全部`、`判断` 五个。其中：

- `引用 3` / `产出 2` —— **纯文本 chip，不可点击**（`CoApisChatResourceBar.tsx` 里是 `<span class="chip">`，无 onClick）；
- `展开 / 收起` —— **唯一一个开关，一次控制两组同时展开/收起**；
- `查看全部` —— 打开 L3 浮窗（会话级台账全量，表格）；
- `判断` —— 打开「判断中枢」浮窗（判官台账 + 判官开关）。

用户读图得到的 expectation 是「引用/产出 各自可点、各出各的」，实际点了没反应；
唯一的开关是行尾那个「展开」。**这是典型的 affordance 错配。**

### 1.3 标题口径：写着「会话资源」，数据只有本轮（问题 4 实锤）

- 聊天区那条的标题 `chat.resources.barTitle` = **「会话资源」**；
- 但它的数据源是 `data.resources` = **本轮**消息事件里的增量（`Chat/index.tsx:2202` → `roundItems(...)`）；
- 会话级全量在左栏那条（`ChatSessionResourcesInline`，走台账 `GET /chats/{id}/resources`，上限 40 行）。

→ 同一句话「会话资源」在页面上出现两次，一个是本轮 5 行、一个是全量 6 行，**用户无法从标题判断作用域**，这就是小蜜蜂说的「现在不知道是当前步骤的」。

### 1.4 已删除文件：聊天侧三条读路径全部 `include_deleted=True`（问题 3 实锤）

API 实测（admin / dev v1.2.18）：

```
GET /api/chats/{chat_id}/resources?limit=200
status:draft 7 · status:deleted 1 · deleted=True 1 · exists=False 1

左栏渲染：  probe / .md / 11-05 15:17        ← 没有任何「已删除」标记
L3 抽屉渲染：probe.md | 产出 | 已删除        ← 灰色 + 红色标签，仍可点
```

后端 `server/coapis/app/routers/chats.py:1051` 三个分支（session / other·all / chat）**全部传 `include_deleted=True`**：

```python
rows = rl.list_session_resources(...,  include_deleted=True)   # L1131
rows = rl.list_chat_view_resources(..., include_deleted=True)  # L1138
rows = rl.list_resources_for_chat(...,  include_deleted=True)  # L1163
```

前端 `CoApisChatResourceBar.tsx:36 resourceStatusOf()` 把 deleted/missing 判成
「灰色 + 已删除/失效标签」但**照旧渲染、照旧可点**；左栏 `Inline.tsx` 连状态标签都不显示。

→ 已删除文件出现在用户面前 = **点下去必然失败**（预览空 / 下载 404），且左栏连标记都没有。

对比：治理侧 `list_resources()`（台账管理页 v1.2.17 用）**已经**过滤软删
（`resource_ledger.py:1545` `Resource.deleted_at.is_(None)`）—— 聊天侧与治理侧两把尺子。

### 1.5 「判断」到底是什么

`CoApisDecisionPanel.tsx` 头部注释自己写着：

> 判断中枢浮窗 —— 判官的台账与开关（v14 §5.2 / U 批）。
> 存在的理由：判官过去判完就沉进库里，用户在聊天里看不到「它判没判、判成什么」。

实测点开：标题「判断中枢」+ 一个刷新按钮，内容空（判官台账当前 0 行 —— 与 seq 48365+ 效果对账结论一致：真判率 19%、outcome 全 pending、生产 0 行）。

→ 它是**判官的审计视图 + 开关面板**，性质上属于运维/审计面，不是聊天用户的任务视图。小蜜蜂判断「应该只是审计日志，不应该显示给用户」= 成立。

### 1.6 组件现状：一份数据，三套渲染（问题 4 根因）

| # | 组件 | 作用域/数据源 | 分组 | 头部 | 删除行 |
| --- | --- | --- | --- | --- | --- |
| L1 | `ChatSessionResourcesInline.tsx` + `inline.module.less` | 会话级台账（≤40 行） | 生成/引用，组头可折叠 | 无头部（挂在会话行下方） | **照显示，无标记** |
| L2 | `CoApisChatResourceBar.tsx` + `.module.css` | **本轮**增量 + 台账补 meta | 引用/产出，一个总开关 | 会话资源 + 2 chip + 展开 + 查看全部 + 判断 | 灰色+标签，可点 |
| L3 | `ChatSessionResources/index.tsx` + `CoApisResourceDrawer.tsx` | 会话级台账（分页表格） | 无分组，表格 6 列 | 抽屉标题 + 刷新 | 灰色+标签，可点 |

数据源**已经统一**（`useChatResourceLedger.getChatResourcesShared` 一份缓存，
L1/L2/L3 共用，实施细则 B4 落地的），**渲染层没收敛**：三套行渲染、三套分组头、
三套删除行策略、三套样式。行内字段口径倒是共用了（`resourceFormat.ts`、
`resourceIcons.tsx`、`helpers.ts`）—— 所以统一渲染的地基是现成的。

## 2. 根因判断（三条各自的「为什么」）

| # | 现象 | 根因 | 性质 |
| --- | --- | --- | --- |
| 1 | 资源行比卡片窄 70%，左边还深 23px | 三层 padding/margin 叠加（B1→D2→D3 三个批次各加各的，谁也没和卡片基线对齐过） | 纯样式债 |
| 2 | 头部 5 控件、chip 不可点、开关只有一个、语义不明 | 头部是「统计 + 开关 + 两个浮窗入口」三件事拼在一行，不是按用户动作设计的 | 交互设计缺陷 |
| 2b | 「判断」出现在聊天里 | v14 判官上线时为自证「判没判」加的临时入口，U 批忘了收进管理面 | 位置错（审计面内容漏进用户面） |
| 3 | 已删除文件留在列表里 | 聊天侧读路径 3 处 `include_deleted=True`；前端策略是「灰显 + 标签」而不是「不显示」 | 口径错（治理口径当成用户口径） |
| 4 | 两个下拉、三套渲染 | 台账数据源统一了，渲染层没统一；作用域靠标题文字表达，标题还撞名 | 架构收尾没做完 |

**结论：小蜜蜂的直觉全部成立。** 数据层已经是「一份」，剩下的是渲染层 + 作用域标签 + 已删除口径三件事。

## 3. 目标形态（站在用户体验角度）

```
┌─ 左栏 300px ─────────────────────┐   ┌─ 聊天区 ──────────────────────────────┐
│ 会话                              │   │  （AI 回答气泡）                        │
│ ┌──────────────────────────────┐ │   │  ...正文...                            │
│ │ 帮我把工作区里这批文   ▾ 19:04│ │   ├──────────────────────────────────────┤
│ ├──────────────────────────────┤ │   │ 本轮引用 3 ▾    本轮产出 2 ▾  查看全部 │
│ │ 生成 3 ▾                     │ │   │  ▸ 点「本轮引用」只展开引用            │
│ │  verify_note.txt  86B 11-04  │ │   │  ▸ 点「本轮产出」只展开产出            │
│ │  report_close.txt 382B 11-02 │ │   │  ─ 展开后（与左栏同一套行组件）：      │
│ ├──────────────────────────────┤ │   │  引用                          预览 下载│
│ │ 引用 3 ▾                     │ │   │  w6_inbox_probe_1794212059.txt  24B   │
│ │  w6_inbox_probe_1794212059   │ │   │  SKILL.md                        1.2KB │
│ └──────────────────────────────┘ │   └──────────────────────────────────────┘
│  ↑ 行宽 = 卡片宽度（283px），左8 右12 与卡片文字基线对齐
└──────────────────────────────────┘
   已删除 / 失效文件：不出现在以上任何一处
   「判断」：从聊天界面移除，收进 管理后台 → 判断中枢（管理员可见）
```

三条硬口径：

1. **作用域写在标签上，不靠用户猜**：左栏 = 「会话全部资源」（现有一切文件，可折叠）；
   聊天区 = 「本轮引用 / 本轮产出」（明确「本轮」二字）。
2. **一个组件**：行的渲染（名称拆干+扩展名、大小·时间、图标、预览能力、可点性）
   只有一份实现，三处（左栏 / 本轮条 / 抽屉表格）共用；分组头 = 开关节。
3. **用户面只给活文件**：已删除/失效的行不进聊天侧任何视图；治理面（台账管理页）
   需要审计历史，走它自己的读路径。

## 4. 落地方案（F1–F5，按依赖排序）

### F1 · 统一行组件 `ResourceRow` + 分组 `ResourceGroup`（治「三套渲染」）

新增 `client/src/pages/Chat/components/ResourceRow.tsx` + `ResourceRow.module.less`：

- `ResourceRow`：一行资源。名称拆 stem/ext、`formatResMeta` 大小·时间、图标、
  `canInlinePreview` 预览能力、`openResource` 三层兜底点击、`deleted/missing` **不渲染**。
  （逻辑直接从 `Inline.tsx:renderGroup` 与 `ChatSessionResources/index.tsx:RowBody` 抽出来，
  字段口径继续用现成的 `resourceFormat.ts` / `resourceIcons.tsx` / `helpers.ts`。）
- `ResourceGroup`：组头 = **开关节**（标签 + 计数 + ▾），点击只展开/收起**自己那一组**。
- `ResourceList`：`items` + `groups`（producer/reference）+ `variant="compact" | "table"`
  + `title` + `onPreview` + `onShowAll`。
- 三个消费点改为只传数据与回调，不再各自写行：
  - `ChatSessionResourcesInline.tsx` → `ResourceList variant="compact"`
  - `CoApisChatResourceBar.tsx` → `ResourceList variant="compact"`
  - `ChatSessionResources/index.tsx`（抽屉）→ `ResourceList variant="table"`（保 6 列 + 排序）

删除：`inline.module.less` 与 `CoApisChatResourceBar.module.css` 里重复的行/组头样式，
统一由 `ResourceRow.module.less` 出（两处的容器外框各自保留）。

> 为什么不是「合并成一个组件挂在左栏、聊天区不挂」：聊天区那条承担的是「本轮我拿到了什么」
> 的即时反馈（产出卡 v23 已合并进它），去掉它 = 用户一轮跑完在气泡附近看不到任何产出入口。
> 所以正确做法是**同一组件、两个容器、两个作用域标签**，而不是砍掉一处。
> 若小蜜蜂就是要「只留左栏一处」，见 §6 D3-B。

### F2 · 左栏宽度与卡片对齐（治问题 1）

`ChatSessionResources/inline.module.less`：

```less
.panel { margin: 0 0 6px 0; padding: 0 0 6px 0; }   // 去 左10/右10/右margin8
.body  { margin: 2px 0 0 0; padding: 0; }           // 去 左2+2
.list  { padding: 2px 12px 2px 8px; }               // 对齐卡片基线：左8 右12
```

→ 行宽 198 → **263px**（+65px，+33%），左右与卡片文字基线齐平；
名称 ellipsis 触发点从 182px 推到 247px（长文件名少截一堆）。

### F3 · 本轮条头部重排 + 摘「判断」（治问题 2 / 2b）

`CoApisChatResourceBar.tsx` 头部（现 264–314 行）改为：

```
本轮引用 3 ▾     本轮产出 2 ▾                        查看全部
[chip=开关]      [chip=开关]                        [进 L3 抽屉]
```

- 两个 chip **自己就是下拉开关**（小蜜蜂要的「下拉直接放在引用、产出上面，各自点击展示各自的」），
  去掉行尾那个总「展开/收起」；
- 无资源时整条不渲染（现行为保持，`items.length === 0 && !loading → null`）；
- 摘「判断」：删 `onJudgment` 挂载（`Chat/index.tsx:2208`），头部只留「查看全部」；
- 标题文案 `chat.resources.barTitle` 从「会话资源」改为「**本轮资源**」（i18n 四语言同步）；
  左栏面板加一行小字标签「**会话全部资源**」，两个作用域从此不打架。

「判断」去处（见 §6 D2）：
- A（推荐）**聊天界面移除，入口收进 管理后台 → 判断中枢**（审计面归审计面）；
- B 完全下线浮窗（判官台账只在治理页看）；
- C 保持现状（不推荐）。

### F4 · 已删除/失效文件不出现在聊天侧（治问题 3）

后端 `server/coapis/app/routers/chats.py`（三个分支 + 两个 count）：
`include_deleted=True` → **`include_deleted=False`**（4 处：L1131 / L1138 / L1163 / L1167，
及 `count_*` 两处）。语义 = 聊天侧只给活文件；治理侧 `list_resources()` 口径不动（本就过滤软删）。

前端兜底（防缓存/旧数据/竞态）：`ResourceRow` 与三个消费点在渲染前统一
`.filter(it => !it.deleted && it.exists !== false)`，
`CoApisChatResourceBar.tsx:resourceStatusOf` 降级为只标 draft/official，删掉 deleted/missing 分支。

副作用交代（不藏尾巴）：
- 左栏/L3 计数会变小（probe.md 这类行消失）—— 这是预期结果；
- `status="deleted"` 的行在**所有 UI** 都不再可见（治理页也看不到软删行，因为它走
  `list_resources` 已过滤）。要看审计历史只有两处：`files/.trash/` 落盘文件 + DB 行。
  若小蜜蜂要治理页能看已删除 → 见 §6 D4-B（给 `/api/resources` 加 `include_deleted` 参数，管理员限定）。
- 现有测试 `tests/unit/test_chat_resources_endpoint_b2.py` 若断言 deleted 行可见，需同步改断言。

## 5. 验收标准（做完必须逐条实测）

1. 左栏资源行 `getBoundingClientRect().width` 与会话卡片同宽（283±1px），左右偏移 = 卡片基线（左 8 / 右 12）。
2. 聊天条头部恰好 3 个可点：`本轮引用 N ▾`、`本轮产出 N ▾`、`查看全部`；点引用只展开引用，点产出只展开产出。
3. 头部**没有**「判断」；`CoApisDecisionPanel` 入口只在管理后台可见。
4. `GET /api/chats/{id}/resources` 返回体里 `deleted=true` 与 `exists=false` 的行数 = 0；左栏/本轮条/L3 抽屉三处 DOM 里搜不到 `probe.md`。
5. 三处视图的行渲染来自 `ResourceRow` 单一实现（`grep -rn "rowMain\|rowName" client/src/pages/Chat/components` 只剩 ResourceRow 一处定义）。
6. 全量 pytest EXIT=0；dev 1.2.19 浏览器实测截图留证；工作树 0 未提交残留；双远端同步 + tag 计数一致（排除 peeled 行）。
