## 〇、先回答"怎么这么多问题"

一句话：**功能都接上了，但没有统一的写入契约、没有与岗位数匹配的资源预算、
没有一把统一的尺子。** 所以每个写点各写各的，每个数字都差一点，合起来看就是"一堆问题"。

按根因分五层，12 个现象收敛到 5 个真凶：

| 层 | 真凶 | 直接导致的现象 |
|---|---|---|
| A 契约层 | 台账写入没有唯一入口，4 处写点各自组装字段 | 档位脏值/身份缺失/岗位名当档位/成本为 0 |
| B 资源层 | 预算与超时是按"2 个判点"定的，现在 5 个岗在抢 | 损耗 52.2%（timeout 28.9% + budget_cap 12.6% + 熔断 10.7%） |
| C 尺子层 | 代码词表 3 档（simple/medium/complex），预检脚本按 4 档校验 | "档位落库率 1.4%" 这个数**是我上轮自己算错的** |
| D 治理层 | 测试/探针数据与真实数据同表且无来源标记 | 台账里 57 行是 e2e/console/空 chat 的测试数据，KPI 被污染 |
| E 环境层 | 生产不在这台机器 | 生产 0 行，无法证明"上线后有用" |

**A+B 是真问题（占 8 项），C 是我上一轮的尺子错误（诚实交代），D+E 是治理和可达性问题。**
功能层面没有任何"炸掉"的缺陷：验收岗 29 行身份齐全、token 4.8 万、成本 4.17 元、
全部 accepted —— **这条标杆证明骨架是通的**，其余是接线与预算的活。

## 二、12 个问题的根因（逐条，带代码位置）

**P1 判档岗身份全空（chat_id=''，turn=0，50 行）**
`plan_gate.py:226 record_ledger()` 只读 `self._ledger_scope`，而 scope 仅在
`react_agent.py:4433 set_ledger_scope(self._decision_scope())` 一条路径注入；
keyword 快速路径（`plan_gate.py:293`）与 `_hub_scope_hook` 未注入 → 写出空身份。
更上游：主链上下文 `runner.py:1712 base_request_context` **没有 chat_id 键**，
且 `set_current_chat_id()` 全仓只有 `routers/console.py:427` 一个调用点 →
WS/企业微信主链上 chat_id 天然取不到（详见批次 2 的证据链）。

**P2 闭环率恒 0（结构性死锁）**
`hub_acceptance.py:210 _backfill_plan_gate()` 按 `chat_id=:chat AND turn=:turn`
回填 outcome；而 P1 决定了 plan_gate 行的 chat_id=''、turn=0 →
**回填条件永远不可能成立**。验收岗自己 29 行漂亮，但永远收不了判档的尾。
这是"判官体系闭环"唯一真正的硬伤。

**P3 档位脏值三种**
- `complexity='plan_gate'`（24 行）：keyword 命中路径把**岗位名**当档位写（`plan_gate.py:239 complexity=level`，keyword 命中时 level 未归一）。
- `complexity='select:low,medium'`（10 行）：技能选择的判词被塞进 complexity 列（`gateway.py:658`）。
- `complexity='medium'/'complex'`：合法，来自 rubric。
- 空 108 行：`gateway.py:658` 明确 `purpose != plan_gate` 时 complexity 写 ""（设计如此，非 bug，但预检按"应落档位"统计就成了红字）。

**P4 词表尺子不一致（我上轮的锅）**
`rubric.py:25 LEVELS = ("simple","medium","complex")` 三档；判则、thinking_budget、
QueryAnalyzer 全用三档。我上轮写的 `scripts/dev_precheck_db.py` 里 `BANDS` 硬编码成
四档（trivial/light/standard/complex）→ 于是合法率被算成 1.4%。
**代码没错，尺子错了。** 必须改成 import 代码常量，禁止两处各写一套。

**P5 成本与 token 可见率 27.7%**
`gateway.py:_cost_of()` 在 `tokens==0` 时返回 0；keyword/cache/breaker/budget/timeout
层天然 0 token → 天然 0 成本（合理），但**没有 reason 标注**，看起来像"没记账"。
llm 层 89 行 token 与成本全齐（48484/4.17 元、12714/5.25 元、6306/2.51 元）→
说明记账通路是好的，缺的是"0 的语义"。

**P6 损耗 52.2% 的三条来源**
- timeout 46 行（28.9%）：判官真实中位 5.4s，`config.py llm_timeout_ms=0` 自适应 → 本地 8000ms/API 5000ms → 长尾（12s）必超时。
- budget_cap 20 行（12.6%）：`judge_max_calls_per_turn=4`，现在一轮要判 判档+技能+改道+验收 ≥4 次 → 天然撞顶，后面的岗直接降级。
- breaker_open 17 行（10.7%）：`breaker_failure_threshold=3` + 冷却 120s，一次长尾超时就连环熄火。
根因是**预算与阈值按 2 个判点设计，岗位增到 5 个后没重算**。

**P7 intent 岗 0 行**
`intent_classifier.py:171` 只用了 `purpose="skill_trigger"`，没有独立 intent 写入点。

**P8 tool_gate 岗 0 行**
无任何调用点（全仓 `purpose=` 只有 acceptance/advisor/skill_trigger/plan_gate 四处）。

**P9 advisor 岗 0 行**
`hub_advisor.py:46 should_advise()` 有起判轮次闸门（`advisor_every_iters`），
短对话（iters 未达阈值）永不触发 → 台账 0 行。属"设计如此但从未观测到"。

**P10 台账卫生**
chat_id='e2e' 21 行、'console:admi' 16 行、chat_id='' 20 行 —— 测试与探针数据
与真实数据同表、无来源列 → 任何 KPI 都是真数与测试数混合，90 天留存后不可审计。

**P11 model 列 5 种写法**
`qwen3-30b-a3b` / `xpu:qwen3-30b-a3b` / `ernie-4.5` / `xpu:ernie-4.5` / `''` →
同一模型两种 ID，成本与耗时无法按模型聚合。

**P12 治理尾巴**
工作树 9 处未提交（小蜜蜂在改的预览窗 4+4 文件、dev 版本桩）；stash 3 条；
tag 本地 93 / 远端 135（远端多出 42 个，来源未查）；生产不在本机 → 无法对账。

### 批次 0 · 尺子对齐（0.5 天，零代码风险，先做）

### 批次 1 · 台账写入契约统一（1.5 天，核心，治 A 层）

新增 **`server/coapis/decision/ledger_contract.py`**（唯一写入口，约 120 行）：

```
write_ledger(source, *, band="", judgment="", action="", layer, model,
             latency_ms, tokens, cost, ids, reason="") -> None
```

职责（把现在散在 4 处的组装逻辑收进一处）：
1. **档位归一**：`band` 必须 ∈ `rubric.LEVELS` 或 `""`；脏值（岗位名、`select:...`）→ 落 `""` 且 `reason="band_invalid:<原值>"`。
2. **身份补全**：`ids` 缺 `chat_id` 时按 `session_id` 反查 `chat_meta` 补齐（现成表，`react_agent.py:2216` 已有同款逻辑）；补不到写 `reason="identity_missing"`。
3. **0 的语义**：非 llm 层 tokens/cost 记 0 且 `reason="no_llm_cost"`；llm 层 tokens=0 写 `reason="usage_missing"`（不再静默）。
4. **model 归一**：统一去 `xpu:` 前缀存净 ID（`model_raw` 保留原值）。

改造 4 个写点全部走契约（**只换调用，不改判断逻辑**）：
`gateway.py:647 _ledger()`、`gateway.py:575 _degrade()`、`plan_gate.py:216 record_ledger()`、`hub_acceptance.py` 回填。

验收：新写入行 档位脏值 = 0；身份齐全率 ≥95%；`reason` 列可解释每一个 0。

### 批次 2 · 闭环死锁修复（1 天，最高优先，治 P1+P2）★生死线

已核实的根因链（三处证据闭合）：
- `app/runner/runner.py:1712 base_request_context = {session_id, user_id, channel, agent_id}`
  —— **主链上下文里没有 `chat_id`**；
- `set_current_chat_id()` 全仓**只有一个调用点** `routers/console.py:427`（控制台路径），
  WS/企业微信等主链从未设置 `chat_id` 这个 ContextVar；
- `react_agent.py:2212 _decision_scope()` 取 `get_current_chat_id()`，取不到就回落到
  `self._request_context.get("chat_id","")` —— 主链同样没有这个键 → 落空串。
⇒ 结论：**主链上所有岗位的 chat_id 天然是空的**；台账里 chat_id 非空的 102 行
全部来自控制台路径（`447b4674…`、`console:admi…`），WS 聊天的判档行 chat_id=''。

| # | 文件 | 改动 |
|---|---|---|
| 2a | `app/runner/runner.py:1712` | `base_request_context` 增加 `"chat_id": <会话 chat_id>`（会话入口已持有 session_id，按 `chat_meta.session_id` 反查即可，`react_agent.py:2216` 已有同款现成逻辑） |
| 2b | 主链会话入口（与 `routers/console.py:352` 对齐） | 调用 `set_session_context(..., chat_id=...)`，让 ContextVar 通道与请求上下文通道**两条都有值**（下游所有消费点受益，不只台账） |
| 2c | `react_agent.py:4433` 一带 | 判岗两条路径（keyword 快速路径 + LLM 路径）都显式 `classifier.set_ledger_scope(self._decision_scope())`，不依赖 `_hub_scope_hook` 的时机 |
| 2d | `plan_gate.py:226 record_ledger()` | `turn` 从 `self._turn_no`/`request_context` 取；取不到写 0 且记 `reason="turn_missing"`（不再静默） |
| 2e | `hub_acceptance.py:210 _backfill_plan_gate()` | 匹配键 `(chat_id, turn)` **命中 0 行时**退化为「同 chat 最近一条 plan_gate」并用 `input_hash` 校验；回填成功写 `outcome_source='acceptance'` |

验收：一条真实多轮 WS 对话跑完 → 判档行 outcome 由验收岗自动从 pending 变
`accepted/partial/failed`，**人手不碰库**；闭环率 ≥60%。

### 批次 3 · 预算与损耗（1 天，治 P6，让用户侧零等待）

| 参数（`decision/config.py`，全部可用 env 覆盖） | 现值 | 建议 | 理由 |
|---|---|---|---|
| `judge_max_calls_per_turn` | 4 | **7** | 5 岗 + 2 余量（改道岗一轮可多次） |
| `breaker_failure_threshold` | 3 | **5** | 本地模型长尾抖动不该连环熄火 |
| `breaker_open_cooldown_s` | 120 | **60** | 冷却过长→台账成片 breaker_open |
| `llm_timeout_ms` | 0→自适应 8000(本地)/5000(API) | **新增软超时 `judge_soft_ms=4000`** | 见下 |

**软超时 + 后台补判（本方案的胜负手）**：超过 4s 先返回规则值继续跑，
判官在后台跑完，把结论**回填同一行台账**（`hit_layer='llm'`、judgment、tokens、cost、
`reason='late_backfill'`）。效果：用户侧 0 等待、损耗从 52.2% 降到 <20%、真判率
统计口径改为"含迟到回填" ≥70%。改动点：`gateway.py:_race_with_budget()` + 新增
`_late_backfill()`（约 40 行），调用方签名不变。

验收：同一批语料复跑 → timeout 行占比 <10%，且每条 timeout 都有对应迟到回填记录。

### 批次 4 · 岗位覆盖（1.5 天，治 P7/P8/P9）
