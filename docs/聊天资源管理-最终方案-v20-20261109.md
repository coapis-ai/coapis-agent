## 0. 范围

聊天中的**资源管理**全链路，含两侧：

- **引用**（智能体用过的资料）：输入区选择（级联菜单）→ 采集（工具执行钩子）→ 呈现（资源条/面板）→ 预览
- **生成**（智能体产出的文件）：写盘（write_file / 脚本 / MCP）→ 登记（台账）→ 呈现 → 预览/下载/删除/版本

底座是**资源台账**（`resources` + `resource_refs`），前端是**四层呈现 + 统一预览浮窗**。

## 3. 体系总览（当前实现形态）

### 3.1 数据层（后端）

```
FS（真相源） ──巡检 sweep/reconcile（单向 FS→DB）──► resources + resource_refs
   ▲                                                    ▲
   │ 写入工具                                          │ 状态/引用计数
   │                                                  │
reference_collector（post_acting 单点采集）      ResourceLedger
  · write_file/edit_file/send_file → producer     register / attach_ref / detach_ref
  · read_file 系 → reference                      mark_status / sweep / list / stats
  · execute_shell_command/脚本/MCP → producer      生命周期 draft→official→orphan→archived
    （v17·F4 扩口，_extract_file_paths +              软删 deleted_at（FS 不动）
      工作区存在性闸门）
finalize_web_references（post_reply 相关性闸门：
  只保留正文实际提及的 URL，10-26 D2-A）

FileLedgerService（file_records = append-only 事件流，永不 DELETE）
  三处接线追加：record / attach_chat / archive_file → 台账
  reconcile 巡检补写台账（v17·F4-B，source='reconcile'）
会话删除 → 释放 refs（chat UUID + session_id 双键）→ refs 空 → orphan（R2）
```

预览/下载走一次性签名票据（D6，JWT 塞 URL 方案已下线）。

## 5. 缺口与补充方案（本方案的增量）

六个缺口，全部来自"设计有、实现无"或"实现跑出来了、设计没接住"。按依赖排序：

### G1 · 分类注册表（= 10-22 审计的 E2，可扩展性主解）【未落地，最优先】

**现状**：kind 的权威定义分散在 4 文件 5 集合（后端 `VALID_KINDS`、`VALID_SOURCES`、
采集器三组 frozenset、前端 `kindIcon`、`PREVIEWABLE_SUFFIXES`），加一类要动 5–7 处，
必然继续漂移。产出物一律 `kind=file`，**没有"内容分类"维**——用户按"报告/代码/数据/
图表"找产出物没有抓手。

**方案**：
1. 后端新增 `foundation/resource_taxonomy.py` 单一权威：
   `kind → {图标, 标签键, 可预览后缀集, 默认内容分类}` + `source → kind` 映射 +
   `扩展名/内容特征 → category` 推断器。
2. 采集器、台账校验、`/api/files/preview` 类型判定、新端点 `GET /api/resources/taxonomy`
   **全部读它**；前端启动拉一次 taxonomy，图标/筛选/预览判定由它驱动
   （`webPreview.ts`/`workspaceLinks.ts` 的表退役为注册表的消费者）。
3. `resources` 加 `category` 列（`report/code/data/chart/doc/config/other`，
   与 kind 正交），迁移 + 存量按扩展名回填；推断器先只做扩展名+简单内容特征
   （代码块占比/表格行数），不上机器学习。
4. 新接入 MCP/自定义工具 → 在注册表声明 kind（配置级），**零改码**。

**工作量**：2.5 人日。**这是"内容分类"唯一主解，越晚做回填越贵。**

### G2 · 台账管理面（= E3）【后端全有，前端零消费者】

**现状**：`GET /api/myfiles/resources`、`/stats`、`POST /sweep` 三端点 2026-10-13 起
就在（admin 门控实测过），前端全仓无引用——台账对管理员是黑盒。dev 实况
orphan 224 条 / deleted 40 条 / backfill 占 59%，**没有任何界面能看到这些**。

**方案**：「我的空间」加"资源台账"页：五维筛选（kind/category/role/source/状态）+
统计卡（按 kind/category/status）+ 巡检报告三列表（fs_missing / orphan / unledgered）+
手动 sweep 按钮。数据层零改动，纯前端消费面。**G1 落地后 category 筛选自动获益。**

**工作量**：1.5 人日。

### G3 · official 发布动作【生命周期半残】

**现状**：状态机冻结了 `draft→official`（"用户确认/交付"），但**没有任何入口调
mark_status(official)**——dev 台账 `official=0` 恒空。状态机三态实际不可达一半，
"哪些产出是定稿"这一维在 UI 和数据上都不存在。

**方案**：预览抽屉 + L3 操作列加"定稿/撤销定稿"按钮 →
`POST /api/myfiles/resources/status {key, status}`（admin/owner 门控，仅允许
draft⇄official 双向，orphan/archived/deleted 不许人为进入）；L1/L2 徽标
"v3 定稿"替代"v3 已更新"优先显示。

**工作量**：0.5 人日。

### G4 · 巡检补扫触发（= v17 拍板 D7-A，落地时被跳过）

**现状**：sweep 只在凌晨 3:00（`start_file_ledger_maintenance(hour=3)`）。白天
脚本产出的文件要等次日才进台账；"会话结束补扫一次"拍板了但没接线。

**方案**：会话删除/会话切换收尾处 fire-and-forget 调 `_sync_reconciled_files`
（带 owner 参数，复用现成函数，10 秒内去抖）；保留夜间全量。

**工作量**：0.5 人日。

### G5 · 非 chat 引用可见性（= 复检 S8，D4=C 遗留，须定稿）

**现状（dev 11-08 实测）**：refs 分布 `chat 180 / session 84 / agent 77`——
36% 的引用挂在聊天 UI 查询口径（join chat ref）之外。用户视角 = 智能体用过的
资料少显示 1/3。当年拍板 C（暂不动）的前提是"归一风险大"。

**定稿建议**：**不做历史数据归一**（agent 77 条多为旧全局 agent 时代产物，归一
无意义且破坏审计），做两件小事：
1. 新写入侧统一：采集/接线处一律优先 `chat`（有 UUID 用 UUID，无则 session_id），
   `agent` 类只留给真·agent 级长期资源；
2. 右侧资源条上半区（scope=session）已能覆盖 session 类——实测确认 84 条可见性，
   若 agent 类仍不可见，在资源抽屉加"其他来源"分组（读面端点加一个
   `referrer_kind=all` 参数）。
**工作量**：0.5 人日（含实测）。

### G6 · 散文件治理（巡检报告的消费闭环）

**现状**：sweep 报告能力齐（fs_missing/orphan/unledgered 三类，上限 200），
10-13 实测 unledgered=1242；`files/` 根历史散文件（upload_test.png 等）10-26 清过
一轮仍会再生。报告没人看、散文件没有"一键归位"。

**方案**：并入 G2 管理页——unledgered 列表提供"归位到 `files/_inbox/`"批量操作
（移动 + `_sync_resource(source='reconcile')`，与巡检口径一致，不新造语义）；
`fs_missing` 列表提供"标 deleted"批量操作。**不做自动清理**（FS 是真相源，
自动删用户文件违反 D3 单向契约）。

**工作量**：0.5 人日（依赖 G2）。

### 已拍板接受的尾巴（定稿记录，不再追）

- 台账启动 backfill 双刃：清数据必须连文件一起移（10-26 实测教训，已写入 MEMORY 坑）；
- 采集覆盖无"应采集总数"分母，只能抽样 E2E 验证（10-26 坑 #222）；
- 软删只对文件，目录仍硬删（目录不是台账对象）。

## 7. 验收口径（合并全家族，终版）

**数据层**
1. `resources`/`resource_refs` 计数与聊天/会话实况对账一致（探针脚本口径）；
2. 删除会话 → 该 chat refs 清零 → 资源流转 orphan（R2）；
3. 脚本（execute_shell_command）产出 xlsx/csv 当轮进台账 + 会话面板可见（F4）；
4. 巡检 sweep 报告三类可列出（fs_missing/orphan/unledgered）。

**呈现层**
5. 三层呈现（L1 卡 / L2 条 / L3 抽屉）数据与台账一致，时间=epoch ms 一把尺子，
   版本 size∥mtime 升版，徽标三态（vN 已更新 / 定稿 / 缺失）；
6. 预览：html/md/txt/图片/office（后端 markdown 渲染）全通；越权 403；
   票据一次性；浮窗可拖/可定住/双击铺满/外点关闭按预览窗六项定稿；
7. 左栏 caret 收起即收起、扩展名不被截、行含时间+大小；
8. 删除=软删进 `.trash/<日期>/` + 台账标 deleted，二次确认；
9. 四语言 i18n 齐平（flat 检查 chat.* 零缺）。

**缺口批（W1–W6 追加）**
10. taxonomy 端点返回注册表，前端图标/筛选/预览判定无本地第二张表（grep 验证）；
11. 存量资源 category 回填率 ≥95%（按扩展名可判者全填）；新产出自动带 category；
12. 管理页可见五维筛选 + 巡检三列表 + sweep 按钮（admin）；
13. 点"定稿"后台账 status=official 且徽标变化；
14. 白天脚本产出入台账延迟 ≤ 会话结束 + 10s（不再等凌晨）；
15. 新会话产生的 refs 只出现 chat/session 两类（agent 类零新增）。
