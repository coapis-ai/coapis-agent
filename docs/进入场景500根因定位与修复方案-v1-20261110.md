# 「进入场景」失败（HTTP 500）根因定位与修复方案 v1

日期：2026-11-10 · 环境：dev 社区版 4300（v1.2.22）· 状态：**未改一行代码，等拍板**

---

## 1. 现象

小蜜蜂在 dev 工作台连点三个场景，前端报：

```
index-BGVtMp0b.js:185 Failed to enter scene: Error: Failed to enter scene
    at T (index-BGVtMp0b.js:86:31541)
```

对应源码 `client/src/components/FloatingChatWindow/index.tsx:154-186`：`enterScene()` 里
`if (!response.ok) throw new Error('Failed to enter scene')` —— 前端只是如实上报后端非 2xx。

## 2. 根因（一句话）

**社区版把 SQLite 场景仓储当成企业版 PostgreSQL 仓储在用**，调用了只有 PG 仓才有的方法
`get_scene_by_id`，直接 `AttributeError` → 500。

### 证据链

1. nginx 访问日志（13:55，用户 Windows/Edge 172.16.6.176，来源 `/workbench`）：
   ```
   POST /api/scenes/document-drafting/enter  500
   POST /api/scenes/meeting-minutes/enter    500
   POST /api/scenes/rural-planning/enter     500
   ```
2. 后端异常日志（同一时刻）：
   ```
   ERROR coapis/app/error_handler.py:127 | Error [10f8f9fc]:
   AttributeError: 'SqliteSceneRepository' object has no attribute 'get_scene_by_id'
   ```
3. 选仓逻辑 `server/coapis/services/scene_agent_service.py:99-119`：
   ```python
   if is_enterprise_installed():                    # ← 只探测「包能否 import」
       if RepositoryFactory.is_initialized():
           self._enterprise_repo = RepositoryFactory.get_scene_repository()
   ```
   启动日志实证：`SceneAgentService using Enterprise PostgreSQL scene repository`（社区版容器里打出来的）。
4. 容器内实测（`docker exec coapis-server-dev`）：
   ```
   is_enterprise_installed = True          # 社区镜像里同样打包了 coapis/enterprise/ 源码，import 必然成功
   SqliteSceneRepository 能力:
     get_scene            True
     get_scene_by_id      False   ← 服务层要调的就是它
     list_scenes          True  (status, category, limit, offset)   # 没有 primary_tag_id
     create_scene         False
     update_scene         False
     delete_scene / get_all / increment_usage / save_many  True
   scenes 表行数 = 57
   ```
5. 企业侧 PG 仓（`coapis-pro/server/coapis/enterprise/database/repositories/scene_repository.py`）
   确实提供 `get_scene_by_id / list_scenes(status, primary_tag_id, limit, offset) / create_scene / update_scene`
   —— 所以企业版没问题，**只有社区版炸**。

### 触发条件（两个都成立才炸）

- `is_enterprise_installed()` 为真：社区镜像内打包了 `coapis/enterprise/` 源码目录 → `import coapis.enterprise` 成功；
- 工厂已初始化且版本为 community → `get_scene_repository()` 返回 `SqliteSceneRepository`
  （`repository_factory.py:205-214`，`fea2179`(2026-09-22) 起接入 M1 场景落库）。

`is_enterprise_installed()` 判的是「包在不在」，不是「版本是不是企业版」——这就是错配的根。

| 接口 | 现状 | 说明 |

| `GET /api/scenes/workbench/scene/{id}` | **500** | 实测：工作台场景卡片详情，公开接口，未登录也炸 |
| `GET /api/scenes/{id}` | 500（需登录） | 同一方法 `get_scene:258` |

## 4. 修复方案

### F1（推荐·治本）：选仓按「版本 + 能力」判，不按「包在不在」判

改动文件：`server/coapis/services/scene_agent_service.py`（仅 `__init__` 里 99–119 段）

```python
        # 选仓判据 = 版本 + 仓储能力，不是「企业包能否 import」。
        # 社区镜像同样打包 coapis/enterprise/ 源码 → is_enterprise_installed()
        # 恒为 True，社区版会拿着 SqliteSceneRepository 去调 PG 仓独有的
        # get_scene_by_id / create_scene / update_scene /
        # list_scenes(primary_tag_id=) → AttributeError → 500（2026-11-10「进入场景」故障）。
        self._enterprise_repo = None
        self._community_repo = None
        try:
            from ..foundation.repository_factory import RepositoryFactory
            if RepositoryFactory.is_initialized():
                repo = RepositoryFactory.get_scene_repository()
                if RepositoryFactory.get_edition() == "enterprise" \
                        and hasattr(repo, "get_scene_by_id"):
                    self._enterprise_repo = repo
                    logger.info("SceneAgentService using Enterprise PostgreSQL scene repository")
                else:
                    self._community_repo = repo
                    logger.info(
                        "SceneAgentService using community SQLite scene repository (%s)",
                        type(repo).__name__,
                    )
        except Exception as e:
            logger.warning(f"Scene repository not available: {e}, falling back to JSON")
```

**为什么这一刀就够**：服务层所有公开方法都有 `if self._enterprise_repo:` 分支，
落到 else 分支后是「`_load_scenes_file()` → `_community_repo.get_all()`（读 DB）→
SceneConfig 对象 → `_save_scenes_file()` → `_community_repo.save_many()`（写 DB）」，
读写都以 SQLite 表为唯一真相源，不再碰 PG 专属方法。已实测该链路成立：
`SceneConfig(**get_all()[0])` 通过校验（57 行全通过），`save_many` 是「load-all → modify → save-all」
配套的全表 reconcile upsert（空列表 no-op，防误清空）。

- 影响方法：`enter_scene / get_scene / list_scenes / create_scene / update_scene / delete_scene` 全部自动走社区分支
- 企业版行为**零变化**（`_enterprise_repo` 赋值条件仍成立）
- 不改前端，不改仓储，不改数据库结构

### F2：启动自检（防再犯）

`__init__` 里若判成 enterprise 分支，加一句硬断言（能力不足直接启动失败并写清原因），
把「运行时用户点击才炸」提前到「启动即暴露」：

```python
        if self._enterprise_repo is not None:
            missing = [m for m in ("get_scene_by_id", "create_scene", "update_scene")
                       if not hasattr(self._enterprise_repo, m)]
            if missing:
                raise RuntimeError(
                    f"scene repository 缺 PG 契约方法 {missing}（edition="
                    f"{RepositoryFactory.get_edition()}），拒绝按企业版分支运行")
```

### F3：测试锁（防回退）

新增 `server/tests/test_scene_repo_wiring.py`（当前 `server/tests` 里**没有任何**用例覆盖这段选仓逻辑）：

1. community 初始化 → 断言 `_enterprise_repo is None`、`_community_repo is not None`
2. 注入假 PG 仓（带 `get_scene_by_id`）+ edition=enterprise → 断言走企业分支
3. 社区版下调用 `get_scene('meeting-minutes')` / `enter_scene(...)` 不得抛 `AttributeError`
4. `list_scenes(tag='office-common')` 必须真过滤（total < 全量）

### F4（可选·不建议本轮做）

给 `SqliteSceneRepository` 补齐 PG 兼容面（`get_scene_by_id`/`create_scene`/`update_scene`/
`list_scenes(primary_tag_id=)`，返回带属性的行对象）。收益是「两条路径合一」；代价是要处理
软删语义、`tenant_id/org_id/deleted_at` 平台列、dict vs 对象两种返回体的差异，风险明显高于 F1。
建议 F1 生效后按需要再评估。

### 附带发现（不在本轮改，记录备查）

1. `_list_scenes_from_repository` 的 `except Exception` 把 `TypeError` 吞成「回落全量」，
   导致标签筛选静默失效——F1 后社区版不再进这条路径，但该吞异常写法仍是隐患。
2. `_update_scene_in_repository` 把 `updated_at` 以 `datetime` 对象塞进 payload，PG 能吃，
   SQLite 会绑定失败（sqlite3 不支持 datetime 适配）。F1 后社区版不走这里，暂不动。
3. 前端把后端 500 统一显示成「进入场景失败」，无 error_id 提示。建议后续：透传后端
   `error_id`（后端 `error_handler` 已生成），便于对日志。

## 8. 本轮挖出并修掉的测试陷阱（写下来，别再踩）

1. **`importorskip` 指向不存在的模块 = 整份文件静默跳过**。标签那份就是典型：模块名复数
   `coapis.models.tags`，宿主与 dev 容器都没有，跑起来一句「skipped」，绿得毫无意义。
2. **夹具不许对共享库做破坏性动作**。`RepositoryFactory.initialize("community")` 在宿主上
   解析到 `/root/.coapis/system/coapis.db`（真实宿主数据目录），我在夹具里做「清空标签/场景表」，
   把该库里 12 条场景真删了（该库是宿主侧 CoApis 安装的数据目录，dev 容器数据在
   `/apps/ai/coapis`，实测未受影响：29 行场景、0 软删；生产 4890 未动）。此后一律：
   **桩件注入工厂，或 JSON 兜底路径 + tmp_path，绝不删共享库**。
3. **依赖合并命名空间的测试要在宿主可跑**：`coapis.foundation.db_engine` 只存在于 dev 容器
   合并命名空间，宿主 `.venv-test` 里 `initialize(community)` 必 ImportError。凡是依赖它的
   用例必须显式 `pytest.skip` 说明，别让它「看起来跑过了」。
