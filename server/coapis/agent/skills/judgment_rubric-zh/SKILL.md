# 判断中枢判则（Judgment Rubric）

CoApis 的判断中枢在五个插手点工作：**判档、审计划、事中改道、加严、验收**。
这五个岗位用的尺子只有一份定义（`coapis/decision/rubric.py`），这里是它的
可检索、可复用版本。

**怎么用来自定义判则**：在你智能体工作区的 `skills/` 下建一个目录名含
`判则` 或 `rubric` 的技能（例如 `判则-我们团队的标准/SKILL.md`），写进你的
标准。判断中枢会自动把它叠加进来并优先于内置判则——判则因此是数据，不是
代码，改它不需要动程序。

## 一、判档（复杂度 + 思考开支）

任务复杂度 + 思考开支判则（一次给出两个结论）：

档位（level）标准：
- simple：一句话就能做完（查、看、改一处、单步操作）。
- medium：2~3 个步骤，或需要读文件、写内容、调用工具。
- complex：多步骤串联、跨系统、需要交付物（报告/部署/重构）。
- 门槛从严：拿不准时往低判。

思考开支（effort）标准（默认不思考，越贵的档越要给到位）：
- minimal：不思考也答得对（查、看、单步操作、纯事实问答、寒暄）。
- low：照标准流程做即可（读文件、写内容、调一个工具）。
- medium：需要先规划步骤（多工具协作、有前后依赖）。
- high：需要多轮规划与自我检查（跨系统、长链、交付物、根因分析）。
- 判为 minimal 必须能说出不思考为什么就够；说不清就给 low。

## 二、事中改道（advisor）

事中改道判则（每轮工具调用后判断，只判"这轮执行有没有跑偏"）：

- 正常推进（continue）：本轮动作在解决用户要的问题；报错但已有明确下一步。
- 建议改道（advise）：出现下列任一情况——
  1. 同一操作连续失败 2 次以上，且每次用同样做法；
  2. 已经读了/搜了 5 次以上，还没有指向任何可执行的下一步；
  3. 当前路径明显不解决用户问题（在改环境外的东西、在答一个用户没问的问题）；
  4. 出现了新事实，使原计划的前提不再成立。
- 只给一句话建议，不超过 60 字，必须说清"下一步该做什么"，不许写"建议谨慎"。
- 判不准就 continue——打扰比漏判更贵。

## 三、验收（acceptance）

完成验收判则（任务收尾时判断，逐条对着判，不许凭"看起来做完了"下结论）：

逐条检查下列验收项，全部成立才算达标：
1. 用户要的东西是否已经交付（有具体内容/文件/结论，不是"我将要做"）；
2. 是否做过验证（跑过命令/读过结果/看过输出），只写代码没验证算不达标；
3. 有没有明显遗留（未跑的测试、未说的报错、被跳过的问题）；
4. 结论是否与用户的要求一致（数量/范围/形式对得上）。

输出：达标 → verdict=met；不达标 → verdict=unmet 并列出**具体缺什么**，
每条必须可执行（"补 X 的测试并给出结果"，不是"再完善一下"）。
拿不准时判 unmet——收尾判严是判官存在的理由。

## 四、判定纪律

- 只输出要求的 JSON，不解释、不安慰、不多余字段。
- 判则与用户明确要求冲突时，**以用户要求为准**，并在结论里说明偏离。
- 判则里"拿不准往低判/判 unmet"是刻意的从严设定，不是保守。
